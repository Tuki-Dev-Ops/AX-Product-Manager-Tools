# 수정 처리

senior-reviewer와 traceability-validator가 올린 항목을 처리하는 절차다.

## 처리 순서

CRITICAL을 먼저 처리한다. 그다음 MAJOR다. MINOR는 마지막에 한 번에 정리한다.

CONFIRM은 수정 대상이 아니다. 사용자에게 올려 결정을 받는다. 결정이 오기 전까지 그 항목에 걸린 다른 수정은 진행하지 않는다.

```text
검토 결과 접수
 ↓
등급 구분?
 ├─ CRITICAL → 담당 단계로 반환 → 수정
 ├─ MAJOR → 담당 단계로 반환 → 수정
 ├─ CONFIRM → 사용자에게 올림 → 결정 대기
 ├─ MINOR → 정리 목록에 적재
 └─ SUGGESTION → 범위 논의 목록에 적재
 ↓
수정 완료
 ↓
추적성 재검증
 ↓
CRITICAL 또는 MAJOR 남음?
 ├─ 예 → 검토 결과 접수로 복귀
 └─ 아니오 → 최종 문서
```

## 담당 배정

| 문제 유형 | 담당 |
| --- | --- |
| 목적, 범위, 요구사항 | pm-consultant |
| 기능, 화면, 권한, 상태 | service-planner |
| API, 데이터, 외부 연계, 인증 | system-planner |
| Flow 누락과 불일치 | flow-designer |

한 항목이 두 역할에 걸치면 상위 역할이 먼저 정리한 뒤 하위 역할이 반영한다. 동시에 고치면 서로 다른 판단이 들어간다.

## 수정 시 지키는 것

- 지적된 항목만 고친다. 고치면서 다른 부분을 함께 바꾸지 않는다.
- 고친 내용을 `_data/changes.yaml`에 적는다. 영향받는 하위 문서를 `affects`에 넣는다.
- 상위 문서를 고쳤으면 하위 문서 상태를 검토 중으로 되돌린다.
- 식별자는 바꾸지 않는다. 내용만 바꾼다.

## 재검증 범위

수정 후 전체를 다시 검사하지 않는다. 아래만 본다.

| 고친 것 | 다시 보는 것 |
| --- | --- |
| 요구사항 | 그 요구사항에 연결된 기능과 Flow |
| 기능 | 그 기능이 나오는 화면과 Flow, 시스템 매핑 |
| 화면 | 그 화면이 나오는 Flow |
| Flow | 그 Flow가 참조하는 기능과 화면 |
| 시스템 구조 | 그 구성요소를 쓰는 기능 |

## 반복 한도

같은 항목으로 세 번 되돌아가면 멈춘다.

세 번 고쳐도 남는 문제는 문서를 잘못 쓴 것이 아니라 결정이 없는 것이다. 그 항목을 의사결정 필요로 바꾸고 사용자에게 올린다. 무엇이 정해지지 않아 막혔는지, 선택지가 무엇인지, 각 선택지가 무엇에 영향을 주는지 함께 적는다.

## 종료

CRITICAL 0건, MAJOR 0건, CONFIRM 처리 완료. 세 조건이 모두 맞을 때 최종 문서로 넘어간다.

MINOR와 SUGGESTION은 남아 있어도 넘어간다. 다만 목록을 최종 검토 결과에 남긴다.
