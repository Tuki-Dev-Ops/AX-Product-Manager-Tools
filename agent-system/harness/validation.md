# 품질 검사

단계가 끝날 때마다 아래 여덟 가지를 검사한다. 하나라도 통과하지 못하면 다음 단계로 가지 않는다.

## 검사 항목

| 항목 | 질문 | 검사 방법 |
| --- | --- | --- |
| 완전성 | 필수 내용이 빠지지 않았는가 | 단계별 필수 항목표 대조 |
| 일관성 | 문서 간 내용이 일치하는가 | 같은 개념을 다루는 문장 비교 |
| 추적성 | 요구사항부터 시스템까지 연결되는가 | `python tools/build_dashboard.py` 결과 확인 |
| 구현성 | 개발자가 만들 수 있는가 | 입력, 처리, 결과, 예외가 모두 있는지 확인 |
| 사용성 | 업무 흐름이 자연스러운가 | Flow를 처음부터 끝까지 따라가기 |
| 운영성 | 운영자가 관리할 수 있는가 | 운영 기능 점검표 대조 |
| 검증성 | QA가 테스트할 수 있는가 | 판정 기준이 숫자나 상태로 적혀 있는지 확인 |
| 용어 | 같은 개념에 같은 용어를 쓰는가 | 용어 정의 절과 본문 대조 |

## 단계별 필수 항목

| 단계 | 필수 항목 |
| --- | --- |
| 02 프로젝트 개요 | 배경, 문제, 목표, 대상 사용자, 범위, 제외 범위 |
| 04 서비스 구조 | 사용자 유형, 권한, 메뉴, 기능, 화면, 상태 |
| 05 기능 정의 | 기능마다 13개 항목 |
| 06 Flow 설계 | 네 가지 Flow, 각 Flow의 9개 확인 항목 |
| 07 시스템 구조 | 구성요소, 기능 매핑, 데이터, 외부 연계, API, 인증과 권한 |

## 운영 기능 점검표

운영 단계에서 빠지기 쉬운 항목이다. 없으면 누락으로 처리한다.

- 계정 관리와 권한 부여
- 접속 기록과 작업 이력
- 데이터 조회와 내려받기
- 잘못된 데이터의 정정 수단
- 외부 시스템 장애 시 대체 처리
- 배치 실패 시 재실행 수단
- 알림 발송 실패 처리
- 운영자용 상태 확인 화면

## 검증성 판정

아래 표현이 있으면 검증할 수 없는 정의다. 고쳐서 다시 쓴다.

| 쓰지 않는 표현 | 고쳐 쓰는 방법 |
| --- | --- |
| 빠르게 처리한다 | 처리 시간의 상한을 적는다 |
| 적절히 표시한다 | 표시할 항목과 순서를 적는다 |
| 필요한 경우 | 조건을 적는다 |
| 대량의 데이터 | 건수 기준을 적는다 |
| 사용자가 원하는 | 선택 가능한 값을 나열한다 |

## 요구사항 문장 검사

ISO/IEC/IEEE 29148 5.2.7을 따른다. 아래를 쓰지 않는다.

최상급, 주관적 표현, 모호한 대명사, 개방형 표현, 빠져나갈 구멍, 전체성 함의.

의무는 평서형으로 적고 권장과 구분한다. 부정문과 수동태를 피한다.

## 자동 검사

```bash
python tools/build_dashboard.py
```

출력에서 아래를 확인한다.

- 미결 항목 건수
- 연결되지 않은 항목 목록

자동 검사는 존재 여부만 본다. 내용이 맞는지는 사람이 읽고 판단한다. 자동 검사를 통과했다고 검증이 끝난 것이 아니다.

## 검사 결과 기록

통과하지 못한 항목은 `_data/issues.yaml`에 등록한다. 통과한 항목은 따로 기록하지 않는다.
