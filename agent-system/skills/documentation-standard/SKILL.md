# 문서 작성 기준

프로젝트 전체 기준은 `CLAUDE.md`에 있다. 이 문서는 Agent가 작업 중 자주 어기는 부분만 다시 정리한 것이다.

## 문장

짧은 평서문으로 쓴다.

| 쓴다 | 쓰지 않는다 |
| --- | --- |
| ~한다 | ~해야 합니다 |
| ~할 수 있다 | ~할 수 있도록 합니다 |
| ~으로 정의한다 | ~하는 것이 필요합니다 |
| ~을 제한한다 | ~하는 것을 권장합니다 |

한 문장에 하나만 담는다. 기능 두 개를 한 문장에 넣지 않는다.

## 쓰지 않는 표현

효율적인, 최적의, 사용자 중심의, 직관적인, 혁신적인, 차별화된, 고도화된, 종합적인, 다양한, 풍부한, 향상된, 체계적으로, 유기적으로, 본질적으로.

이런 말이 들어간 문장은 대개 아무것도 말하지 않는다. 무엇을 하는지로 바꿔 쓴다.

```text
쓰지 않는다  사용자 편의성을 극대화한다.
쓴다        고객은 행사, 지역, 기간을 조건으로 검색하고 결과에서 상세 정보를 확인한다.
```

## 관점 분리

사용자 관점과 시스템 관점을 한 문장에 섞지 않는다.

```text
섞였다   사용자가 로그인 버튼을 클릭하면 시스템은 인증 API를 호출하여 토큰을 발급한다.
사용자   계정과 비밀번호를 입력하고 로그인한다.
시스템   인증 요청을 받아 계정을 확인하고 접속 자격을 발급한다.
```

## 이름

기능명과 화면명은 짧은 명사로 짓는다.

| 쓴다 | 쓰지 않는다 |
| --- | --- |
| 회원 목록 | 회원 정보 관리 화면 |
| 주문 취소 | 주문을 취소할 수 있는 기능 |
| 매출 조회 | 매출 정보를 효율적으로 조회 |

한 번 부여한 이름과 식별자는 바꾸지 않는다. 삭제되어도 재사용하지 않는다.

## 용어

한 개념에 한 단어만 쓴다. 다르게 쓰려면 무엇이 다른지 정의한다.

```text
회원   서비스에 가입한 사용자
고객   실제로 주문한 사람
관리자 운영 권한을 가진 사용자
```

## 상태명

업무 용어로 정하고 문서 전체에서 통일한다.

```text
대기  처리 중  완료  실패  취소
```

같은 뜻을 완료, 성공, 처리완료로 번갈아 쓰지 않는다.

## 오류 문구

무엇이 일어났고 무엇을 하면 되는지 적는다.

| 상황 | 문구 |
| --- | --- |
| 일반 실패 | 요청을 처리하지 못했습니다. 잠시 후 다시 시도해 주세요. |
| 입력 오류 | 비밀번호가 일치하지 않습니다. |
| 서버 오류 | 서버와 연결할 수 없습니다. 잠시 후 다시 시도해 주세요. |

오류 코드를 사용자에게 그대로 보이지 않는다.

## 표

비교가 필요할 때만 쓴다. 문서를 구조적으로 보이게 하려고 만들지 않는다.

## 요구사항 문장

ISO/IEC/IEEE 29148 5.2.7을 따른다. 아래를 쓰지 않는다.

최상급, 주관적 표현, 모호한 대명사, 개방형 표현, 빠져나갈 구멍, 전체성 함의.

```text
쓰지 않는다  시스템은 가능한 한 빠르게 응답해야 한다.
쓴다        매출 조회 결과는 3초 이내에 표시한다.
```

## 판단 표기

| 표기 | 기준 |
| --- | --- |
| 가정 | 문맥상 판단, 근거 문장 없음 |
| 확인 필요 | 결정이 있어야 정해진다 |
| 의사결정 필요 | 선택지가 있고 고르면 된다 |

내부 용어를 사용자 문서에 그대로 쓰지 않는다.

## 마지막 확인

문장을 쓴 뒤 세 가지를 본다.

1. 이 문장이 없으면 무엇이 달라지는가. 달라지는 게 없으면 지운다.
2. 개발자가 이걸로 만들 수 있는가.
3. QA가 이걸로 판정할 수 있는가.
