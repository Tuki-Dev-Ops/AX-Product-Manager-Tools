# 문서 검토

작성된 문서를 그대로 믿지 않는다. 쓴 사람의 판단이 맞는지 다시 따진다.

## 검토 질문 18개

| 번호 | 질문 | 확인 방법 |
| --- | --- | --- |
| 1 | 목적과 기능이 연결되는가 | 기능 하나를 골라 목적까지 거슬러 올라간다 |
| 2 | 문제와 해결 방법이 연결되는가 | 문제 목록과 기능 목록을 대조한다 |
| 3 | 사용자와 기능이 연결되는가 | 담당 사용자가 없는 기능을 찾는다 |
| 4 | 권한이 정의되어 있는가 | 기능과 사용자 유형 교차표를 본다 |
| 5 | 서비스 구조와 메뉴가 일치하는가 | 03과 05를 대조한다 |
| 6 | 기능과 Flow가 일치하는가 | Flow에 없는 기능, 기능에 없는 단계를 찾는다 |
| 7 | Flow에 예외가 있는가 | 실패 경로 없는 Flow를 찾는다 |
| 8 | 기능에 데이터가 정의되어 있는가 | 관련 데이터가 빈 기능을 찾는다 |
| 9 | 데이터와 시스템이 연결되는가 | 저장 위치가 없는 데이터를 찾는다 |
| 10 | 외부 연계가 빠지지 않았는가 | 결제, 알림, 인증, 지도, 인쇄를 확인한다 |
| 11 | 같은 기능이 다른 이름으로 있는가 | 입력과 결과가 같은 기능을 찾는다 |
| 12 | 용어가 일관적인가 | 같은 개념의 단어를 문서별로 모아 본다 |
| 13 | 모호한 요구사항이 있는가 | 판정 기준이 없는 문장을 찾는다 |
| 14 | 운영 상황이 고려되었는가 | 운영 점검표를 대조한다 |
| 15 | QA가 검증할 수 있는가 | 테스트 판정 기준을 만들 수 있는지 본다 |
| 16 | 임의로 확정한 내용이 있는가 | 근거 없이 단정한 문장을 찾는다 |
| 17 | 과도하게 확장된 기능이 있는가 | 요구사항으로 올라가지 못하는 기능을 찾는다 |
| 18 | 필요한 기능이 빠졌는가 | 운영 점검표와 예외 목록을 대조한다 |

## 등급

| 등급 | 기준 | 처리 |
| --- | --- | --- |
| CRITICAL | 이대로면 만들 수 없거나 잘못 만든다 | 즉시 수정 |
| MAJOR | 서비스나 시스템에 영향을 준다 | 수정 후 재검증 |
| MINOR | 문서 품질과 명확성 | 정리 단계 |
| CONFIRM | 결정이 있어야 판단할 수 있다 | 담당자에게 올림 |
| SUGGESTION | 넣으면 좋으나 필수는 아니다 | 범위 논의 |

등급을 정할 때 기준은 하나다. 개발과 QA가 이 문서로 일을 시작할 수 있는가.

## 판정 서식

```text
[CRITICAL] 결제 실패 후 주문 상태가 정의되어 있지 않다
  위치: docs/07_기능명세.md 결제 승인
  사실: 승인 실패 시 주문을 어떤 상태로 두는지 문장이 없다.
  영향: 개발자가 임의로 정하게 되고 QA는 검증 기준을 만들 수 없다.
  조치: 실패 시 상태와 재시도 정책을 기능 명세에 정의한다.
```

사실과 판단을 나눈다. 사실은 문서에 있는 문장이거나 없는 것이다. 판단은 그로 인해 생길 결과다.

## 운영 점검표

- 데이터가 없을 때 화면
- 담당자 부재 시 업무 처리
- 외부 시스템 무응답 시 처리
- 잘못 입력한 데이터의 정정
- 작업 이력 추적
- 권한 없는 접근

## 모호한 표현

아래가 있으면 검증할 수 없다.

빠르게, 적절히, 필요한 경우, 대량의, 사용자가 원하는, 다양한, 유연하게.

숫자나 상태로 바꿔 쓴다.

## 하지 않는 것

- 문서를 직접 고치지 않는다. 수정은 담당 역할이 한다.
- 문장 다듬기를 MAJOR로 올리지 않는다.
- 범위를 늘리는 제안을 CRITICAL이나 MAJOR로 올리지 않는다.
