# 프로젝트 분석

## 언제 쓰는가

기존 자료는 있는데 무엇을 만드는지 정리되지 않은 상태. 또는 자료끼리 다른 말을 하는 상태.

## 절차

### 1. 자료를 분류한다

읽기 전에 무엇이 있는지 나눈다.

| 구분 | 신뢰도 | 예 |
| --- | --- | --- |
| 확정 자료 | 높음 | 계약서, 확정된 요구사항, 승인된 정책서 |
| 작성 중 자료 | 중간 | 기획서 초안, 화면설계서 |
| 참고 자료 | 낮음 | 회의록, 메모, 경쟁사 자료 |

충돌하면 신뢰도가 높은 쪽을 따른다. 신뢰도가 같으면 최신 것을 따르되 충돌로 기록한다.

### 2. 사실만 뽑는다

자료를 읽으며 아래 다섯 가지만 뽑는다. 이 단계에서 해석하지 않는다.

- 누가 쓰는가
- 무엇을 하는가
- 왜 필요하다고 적혀 있는가
- 무엇이 이미 있는가
- 무엇을 하지 않는다고 적혀 있는가

원문 위치를 함께 적는다. 나중에 근거를 대야 한다.

### 3. 문제를 정의한다

목적이 아니라 문제를 적는다. 둘은 다르다.

| 구분 | 예 |
| --- | --- |
| 목적 | 매출 통계를 제공한다 |
| 문제 | 행사가 끝난 뒤에야 어느 상권이 잘 팔렸는지 알 수 있어 다음 행사 구성에 반영하지 못한다 |

문제를 적을 때 아래를 채운다. 채우지 못하면 문제가 아직 정의되지 않은 것이다.

- 누가 겪는가
- 언제 겪는가
- 지금은 어떻게 하고 있는가
- 그래서 무엇이 안 되는가

### 4. 목표를 정의한다

문제 하나에 목표 하나를 대응시킨다. 목표는 달성 여부를 판단할 수 있게 적는다.

```text
문제  행사 종료 후에야 상권별 실적을 알 수 있다
목표  행사 진행 중 일 단위로 상권별 매출을 확인할 수 있다
```

### 5. 범위를 나눈다

포함 범위보다 제외 범위를 먼저 적는다. 제외를 적지 않으면 범위는 계속 늘어난다.

| 구분 | 적는 것 |
| --- | --- |
| 포함 | 이번에 만드는 것 |
| 제외 | 이번에 만들지 않는 것과 그 이유 |
| 연계만 | 만들지 않지만 연결은 하는 것 |

### 6. 요구사항으로 바꾼다

목표를 요구사항 문장으로 바꾼다. 한 문장에 하나만 담는다.

```text
REQ-001  본사 운영자는 행사, 상권, 브랜드, 기간을 조건으로 매출을 조회할 수 있다.
```

주어, 대상, 동작이 모두 들어간다. 그렇게 쓰면 나중에 기능으로 바로 이어진다.

## 표기

| 표기 | 기준 |
| --- | --- |
| 확정 | 자료에 문장이 있다 |
| 가정 | 문맥상 판단, 근거 문장 없음 |
| 확인 필요 | 결정이 있어야 정해진다 |

가정과 확인 필요는 `_data/issues.yaml`에 등록한다.

## 자주 나오는 문제

| 상황 | 처리 |
| --- | --- |
| 자료마다 사용자 유형 이름이 다르다 | 하나로 정하고 나머지를 별칭으로 기록. 용어 정의 절에 남긴다 |
| 목적만 있고 문제가 없다 | 목적을 그대로 두고 문제를 확인 필요로 올린다 |
| 범위가 적혀 있지 않다 | 자료에 나온 기능만 포함으로 보고, 나머지를 제외로 적은 뒤 확인받는다 |
| 기대효과가 수치로 적혀 있다 | 근거 자료가 있는지 확인한다. 없으면 수치를 빼고 방향만 적는다 |
