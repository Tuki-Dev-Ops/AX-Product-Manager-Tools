# 서비스 구조화

## 원칙

기능을 나열하지 않는다. 아래 연결을 만든다.

```text
사용자 → 목적 → 업무 → 서비스 → 기능 → 화면 → 데이터
```

## 절차

### 1. 사용자 유형을 정의한다

역할이 다르면 다른 유형이다. 소속이 다른 것만으로는 유형을 나누지 않는다.

| 항목 | 내용 |
| --- | --- |
| 식별자 | UT-01 |
| 이름 | 본사 운영자 |
| 하는 일 | 기준정보 등록, 메뉴 배포, 매출 분석 |
| 접근 범위 | 전체 매장 |
| 접근 수단 | 내부 어드민 |

### 2. 업무를 나눈다

사용자 유형마다 실제로 하는 일을 적는다. 화면이 아니라 일이다.

```text
본사 운영자
 ├─ 매장을 연다
 ├─ 메뉴를 바꾼다
 ├─ 실적을 본다
 └─ 계정을 관리한다
```

### 3. 기능을 뽑는다

업무 하나를 기능으로 쪼갠다. 기능 이름은 명사나 동작 중심으로 짧게 짓는다.

| 쓰는 이름 | 쓰지 않는 이름 |
| --- | --- |
| 매장 등록 | 매장 정보를 등록할 수 있는 기능 |
| 매출 조회 | 매출 정보를 효율적으로 조회 |

### 4. 기능을 상세화한다

기능마다 아래 13개를 채운다.

```text
기능 ID      FN-104
기능명       매장 등록
목적         행사와 상권 아래에 매장을 만들고 주문 채널을 연다
대상 사용자   UT-01 본사 운영자
선행 조건    행사와 상권이 등록되어 있다
입력         소속, 사업자 정보, 주소와 좌표, 영업시간, 채널 사용 여부
처리         필수 항목 검증 → 사업자번호 중복 검사 → 지점번호 중복 검사 → 저장
결과         매장이 생성되고 매장 상세로 이동한다
예외         사업자번호 중복 시 저장하지 않고 해당 항목을 표시한다
권한         매장 관리 권한
상태값       영업, 일시중지, 종료
관련 화면    ADM-STOR-FORM, ADM-STOR-DETAIL
관련 데이터   매장, 브랜드, 상권
```

### 5. 화면을 정의한다

기능을 화면에 배치한다. 한 화면에 여러 기능이 들어갈 수 있다. 한 기능이 여러 화면에 걸칠 수도 있다.

화면 식별자는 `{채널}-{업무}-{유형}` 형식으로 만든다. 한 번 부여하면 바꾸지 않는다.

### 6. 상태를 정의한다

상태마다 진입 조건과 다음 상태를 적는다.

| 상태 | 진입 조건 | 다음 상태 |
| --- | --- | --- |
| 접수 대기 | 결제 승인 완료 | 조리 전, 취소 |
| 조리 전 | 매장이 접수함 | 조리 완료, 취소 |
| 조리 완료 | 매장이 완료 처리함 | 수령 완료 |
| 수령 완료 | 고객이 수령함 | 종결 |
| 취소 | 고객 요청 또는 매장 거절 또는 미응답 | 종결 |

### 7. 예외를 정의한다

기능마다 실패 상황을 적는다. 아래 네 가지는 반드시 확인한다.

- 입력이 잘못된 경우
- 권한이 없는 경우
- 대상 데이터가 없거나 이미 바뀐 경우
- 외부 시스템이 응답하지 않는 경우

## 권한 정의

기능과 사용자 유형을 표로 교차시킨다. 빈 칸이 있으면 그 조합은 접근 불가라는 뜻이므로 명시한다.

| 기능 | 본사 운영자 | 가맹 관리자 | 고객 |
| --- | --- | --- | --- |
| 매장 등록 | 가능 | 불가 | 불가 |
| 품절 설정 | 가능 | 가능 | 불가 |
| 주문 생성 | 불가 | 불가 | 가능 |

## 자주 나오는 문제

| 상황 | 처리 |
| --- | --- |
| 기능은 있는데 사용자가 없다 | 배치나 연계인지 확인한다. 아니면 불필요한 기능이다 |
| 같은 일을 두 기능으로 정의했다 | 대상 사용자, 입력, 결과, 데이터가 같으면 합친다. 어느 이름을 남길지는 제안만 한다 |
| 화면이 없는 기능이 있다 | 배치, API, 알림 중 무엇인지 밝힌다 |
| 상태 이름이 문서마다 다르다 | 용어 정의 절에 하나로 고정하고 전부 바꾼다 |
