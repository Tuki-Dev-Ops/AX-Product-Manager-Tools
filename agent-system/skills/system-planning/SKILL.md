# 시스템 구조 설계

## 절차

### 1. 기능을 시스템 끝까지 따라간다

기능 하나마다 아래를 채운다. 중간이 비면 구현할 수 없다.

```text
기능 → 화면 → API → 처리 로직 → 데이터 → 데이터베이스 → 외부 시스템 → 결과
```

| 기능 | 화면 | API | 데이터 | 외부 |
| --- | --- | --- | --- | --- |
| 매장 등록 | ADM-STOR-FORM | 매장 등록 | 매장, 브랜드 | 좌표 조회 |
| 결제 승인 | WEB-PAY-WAIT | 결제 승인 요청 | 주문, 결제 | 결제대행사 |

### 2. 조사한다

구성 요소를 고르기 전에 조사한다. 조사 없이 통상적인 구성을 적지 않는다.

조사할 것.

- 같은 업종에서 실제로 쓰는 구성
- 각 선택지의 제약과 비용 구조
- 연동 대상의 공식 문서에 적힌 연결 방식
- 법령이나 규제에서 요구하는 조건

조사 결과는 `research/`에 원본을 남기고, 문서에는 판단으로 바꿔 적는다.

### 3. 선택을 기록한다

결론만 적지 않는다.

```text
결정 대상   메뉴 마스터를 키오스크에 내려주는 방식
선택지     실시간 조회 / 주기적 내려받기 / 변경 시 전송
채택       주기적 내려받기 + 변경 시 전송
근거       매장 네트워크가 불안정하고 유휴 시간이 길다. 조사 원본은 research/키오스크_조사.md
조건       단말 상시 연결이 보장되면 실시간 조회로 바꿀 수 있다
```

### 4. 시스템 구조를 그린다

계층을 나눈다.

```text
사용자
 ↓
Web / Mobile / Kiosk
 ↓
Frontend
 ↓
API
 ↓
Backend
 ├─ 인증
 ├─ 권한
 ├─ 업무 처리
 ├─ 데이터 처리
 ├─ 파일 처리
 └─ 알림
 ↓
Database
 ↓
External System
```

각 칸에 실제 구성 요소를 넣는다. 기술명을 확정할 수 없으면 역할 이름만 적는다.

### 5. API 요구사항을 적는다

경로와 스키마는 정하지 않는다. 설계 단계의 일이다.

| 항목 | 내용 |
| --- | --- |
| 목적 | 무엇을 하는가 |
| 호출 주체 | 누가 부르는가 |
| 입력 | 무엇을 보내는가 |
| 출력 | 무엇을 돌려받는가 |
| 실패 응답 | 실패하면 무엇을 돌려주는가 |
| 권한 | 누가 부를 수 있는가 |
| 멱등성 | 같은 요청이 두 번 와도 되는가 |

결제, 주문 생성처럼 중복 실행이 금액에 영향을 주는 API는 멱등성을 반드시 적는다.

### 6. 데이터 구조를 적는다

업무 객체 단위다. 테이블 설계로 내려가지 않는다.

| 항목 | 내용 |
| --- | --- |
| 객체명 | 주문 |
| 식별자 | 주문번호 |
| 주요 속성 | 매장, 채널, 금액, 상태, 주문 시각 |
| 관계 | 매장 1 : 주문 N |
| 보관 기간 | 5년 |
| 개인정보 | 주문자명, 휴대폰번호 |

### 7. 외부 연계를 적는다

연계마다 아래를 채운다.

- 연동 대상과 목적
- 연동 방식과 방향
- 인증 방식
- 실패 시 처리
- 재시도 정책
- 장애 시 대체 수단

대체 수단이 없으면 그 사실을 적는다. 없다는 것도 결정이다.

## 기술 결정 필요

요구사항에 없는 기술을 확정하지 않는다. 아래 형식으로 분리한다.

```text
[기술 결정 필요] 이미지 저장소
선택지    클라우드 객체 저장소 / 자체 서버 저장
조건      매장 수와 이미지 갱신 빈도에 따라 달라진다
영향      정해지지 않으면 이미지 업로드와 배포 기능의 처리 방식을 확정할 수 없다
```

## 운영 요구사항

아래를 빠뜨리지 않는다.

- 접속 기록과 작업 이력 보관
- 배치 실행 결과 확인과 재실행
- 알림 발송 실패 처리
- 외부 시스템 상태 확인
- 데이터 백업과 복구
- 개인정보 접근 통제
