# Flow 설계

## 네 가지를 분리한다

| 구분 | 주어 | 무엇을 그리는가 | 언제 필요한가 |
| --- | --- | --- | --- |
| User Flow | 고객, 운영자 | 사용자가 무엇을 하는가 | 화면 설계 전 |
| Business Flow | 담당자 | 업무가 어떻게 처리되는가 | 승인, 반려, 상태 전이가 있을 때 |
| System Flow | 시스템 | 무엇이 무엇을 부르는가 | 외부 연계나 비동기 처리가 있을 때 |
| Data Flow | 데이터 | 데이터가 어디서 나서 어디로 가는가 | 검증, 가공, 집계가 있을 때 |

하나로 합치면 사용자 행동과 시스템 처리가 섞여 어느 쪽도 검증할 수 없다.

## 절차

### 1. 시작과 끝을 정한다

Flow를 그리기 전에 두 가지를 먼저 적는다.

- 무엇이 있어야 시작하는가
- 무엇이 되면 끝나는가

이걸 못 적으면 아직 Flow를 그릴 단계가 아니다.

### 2. 성공 경로를 먼저 그린다

가장 흔한 경우 하나만 처음부터 끝까지 그린다. 분기를 넣지 않는다.

### 3. 분기를 넣는다

판단이 필요한 자리를 찾아 판단 도형으로 바꾼다. 각 출구에 조건 값을 적는다.

### 4. 실패 경로를 넣는다

분기마다 실패했을 때 어디로 가는지 적는다. 세 가지 중 하나다.

- 앞 단계로 되돌아간다
- 다른 Flow로 넘어간다
- 종료한다

### 5. 예외를 넣는다

분기와 예외는 다르다. 분기는 예상된 갈림길이고, 예외는 정상 처리가 불가능해진 상태다.

예외는 별도 Flow로 뺀다. 본선에서는 그 Flow를 부르기만 한다.

## 표기 규칙

ISO 5807을 따른다. 흐름은 위에서 아래, 왼쪽에서 오른쪽이다.

| 도형 | 쓰는 곳 | 표기 |
| --- | --- | --- |
| 단자 | 시작과 끝 | 첫 줄과 마지막 줄, 또는 복귀·종료로 끝나는 문장 |
| 처리 | 일반 단계 | 그냥 적는다 |
| 판단 | 분기 | 문장 끝에 물음표 |
| 데이터 | 입력과 출력 | 입력, 출력, 표시, 발송, 스캔, 안내로 끝맺는다 |
| 정의된 처리 | 다른 Flow 호출 | Flow 식별자만 적는다 |

```text
로그인 화면
 ↓
계정·비밀번호 입력
 ↓
인증 성공?
 ├─ 아니오 → 안내 표시 → 계정·비밀번호 입력으로 복귀
 └─ 예 → 다음
 ↓
FL-112
 ↓
종료
```

되돌아가는 경로는 `대상 단계로 복귀`로 끝맺는다. 대상 이름은 같은 Flow 안의 단계 이름과 글자까지 같아야 연결된다.

## 세 단계로 나눈다

| 단계 | 범위 | 예 |
| --- | --- | --- |
| 전체 | 채널이나 조직을 가로지른다 | 기준정보 등록부터 매출 집계까지 |
| 서비스별 | 한 채널 안에서 끝난다 | 본사 운영자의 매장 개설 |
| 화면별 | 화면 하나 안에서 끝난다 | 매장 등록 화면의 입력과 검증 |

위 단계는 아래 단계를 정의된 처리로 부른다. 같은 내용을 두 단계에 적지 않는다.

## 작성 확인 항목

Flow마다 아홉 가지를 확인한다.

시작 조건, 사용자 행동, 시스템 처리, 업무 처리, 분기 조건, 성공 결과, 실패 결과, 예외 상황, 종료 조건.

## 자주 나오는 문제

| 상황 | 처리 |
| --- | --- |
| 분기 없는 판단 도형 | 판단이 아니다. 처리로 바꾼다 |
| 실패 경로가 없다 | 미완성이다. 실패했을 때 어디로 가는지 적는다 |
| 되돌아가는 선이 연결되지 않는다 | 대상 이름이 단계 이름과 다르다. 글자를 맞춘다 |
| 기능 목록에 없는 단계가 나온다 | 기능을 추가하거나 단계를 뺀다. Flow에서 기능을 만들지 않는다 |
| Flow가 너무 길다 | 화면별 Flow로 쪼개고 본선에서 부른다 |

## 완료 기준

- 기능 목록의 기능이 어느 Flow에든 나온다
- 화면 목록의 화면이 어느 Flow에든 나온다
- 모든 판단에 두 개 이상 출구가 있고 조건 값이 적혀 있다
- 되돌아가는 대상이 그 Flow 안에 실제로 있다
