# 조사 자료 — 인프라 아키텍처, 결제·단말 연동

조사일 2026-09-03. 03 서비스 구조의 근거 자료다. 기획 판단은 `docs/02_기획검토.md`와 `docs/03_서비스구조.md`에 정리한다.

## 0. 아키텍처보다 먼저 확정해야 할 규제 사실

**본사가 가맹점 대금을 수취해 정산하면 전자지급결제대행업 등록 대상이 될 수 있다.** 금융위원회는 플랫폼이나 유통업체 본사가 전자적 방법으로 대가 정산을 대행하거나 매개하는 경우 등록 대상이라고 설명한다. 배달앱, 숙박플랫폼, 오픈마켓이 이미 등록되어 있다. 반대로 외부 PG사가 정산을 전담하고 플랫폼은 정산에 필요한 정보만 제공하면 등록 의무가 없다. 미등록 시 3년 이하 징역 또는 2천만원 이하 벌금이다.

결제·정산 계약 구조를 먼저 정하지 않으면 데이터 모델과 인프라 범위를 확정할 수 없다.

## 2. 권장 구성

### 클라우드·기반

* AWS 서울 리전을 쓴다. 국내 이용 기업이 가장 많아 인력 확보와 사례가 충분하고, 공공 조달이 없으므로 클라우드 보안인증이 필요 없다.
* 컨테이너는 ECS on Fargate로 시작한다. 쿠버네티스는 전담 운영 조직을 전제하고 클러스터 고정비가 붙는다.
* 데이터베이스는 PostgreSQL 계열을 쓴다. 행사, 상권, 매장, 기간의 다차원 매출 집계가 요구사항인데 MySQL은 다차원 집계 문법이 제한된다.
* 개인정보는 서울 리전 밖으로 내보내지 않는다. 국외이전 절차를 피할 수 있다.

### 서비스 구성

* 모듈러 모놀리스 하나에 배치와 워커를 별도 실행 단위로 둔다. 코드는 하나, 실행 단위는 주문 API, 어드민, 배치, 워커로 나눈다.
* 어드민과 주문 API는 같은 코드베이스를 쓰되 배포 단위를 분리한다. 배민은 메인 DB를 공유하던 구 어드민이 전체 장애로 번져 통폐합했다.
* 배치는 API와 같은 프로세스에 두지 않는다. 자원 고갈 문제가 실제로 보고되었다.
* 메시지 큐는 키오스크 단계에서 도입한다. 초기에는 커밋 후 발행과 실패 로그로 충분하다.

### 데이터

* 1~2단계는 운영 DB 단독으로 간다.
* 통계는 처음부터 집계 테이블을 둔다. 집계 테이블은 적재 시작 이후만 조회할 수 있으므로 늦게 만들면 과거 구간이 빈다.
* 집계는 애플리케이션이 아니라 DB에서 한다. 측정에서 2만5천건 기준 DB가 8초, 애플리케이션이 12초였다.
* 읽기 전용 복제본은 리포팅이 운영에 영향을 주기 시작할 때 붙인다.
* 분석 저장소는 4단계 이후에 판단한다. 도입 기준은 데이터 건수가 아니라 분석 쿼리가 운영 커밋을 지연시키는 시점이다.
* 캐시는 세션과 조회에 쓰되, 캐시 미스 시 DB로 부하가 쏠리는 경로에 차단 장치를 둔다. 컬리가 이 경로에서 장애를 겪었다.

### 결제

* 웹앱은 PG 인증결제와 서버 승인 구조를 쓴다. 카드정보를 서버에 저장하지 않는 표준 구조다.
* 승인 전 금액 위변조 검증을 서버에서 반드시 한다. 토스페이먼츠는 인증 후 10분 내 승인을 요구한다.
* 멱등키를 쓴다. 토스페이먼츠는 최대 300자, 15일 유효다.
* 인증은 성공했으나 승인을 호출하지 않은 상태를 별도 상태값으로 관리한다.
* PG와 VAN 모두 망취소를 자동 처리한다.
* 결제 데이터는 플랫폼 자체 결제 식별자를 최상위 키로 두고 채널별 식별자를 옵션으로 붙인다. 승인번호가 PG와 VAN 공통 필드다.
* 매출은 통합하되 정산은 분리해 표기한다. VAN 대금은 카드사가 가맹점에 직접 지급하고 플랫폼을 거치지 않는다.
* 취소 시 원거래 참조 키가 채널마다 다르다. PG는 결제 키, VAN은 거래일련번호다.

### 키오스크

* Windows IoT Enterprise를 쓴다. 국내 VAN 에이전트가 PC 상주 데몬이고, 오케이포스는 안드로이드 키오스크를 자사 범위 밖으로 명시한다.
* 키오스크 모드는 에디션을 먼저 확인한다. 단일 앱 키오스크는 Enterprise 또는 Education 전용 기능이 필요하다.
* 오프라인 카드결제는 설계하지 않는다. 국내 VAN 승인은 온라인 실시간이 전제다. 오케이포스의 오프라인 PG는 오프라인 승인이 아니라 PG 거절 시 VAN으로 재시도하는 결제 경로 이중화다.
* 네트워크는 유선과 이동통신 라우터로 이중화한다. 행사장·팝업 운영이 있으면 필수다. 올리브영은 1,370개 매장 3,500대 운영에서 간헐적 단절이 빈번하다고 보고했다.
* 원격 업데이트 배포를 규제 대응 수단으로 본다. 롯데리아는 접근성 기능을 소프트웨어 업데이트로 전국 매장에 적용했다.

### 하이브리드 웹앱

* 모바일 웹을 기본으로 한다. 웹뷰 래핑은 배제한다. 앱스토어 미등록 전제에서 iOS 배포 경로가 없다.
* 웹뷰를 쓰지 않는 것이 오히려 유리하다. 모바일 브라우저는 카드사 앱 호출과 복귀를 자동 처리한다.
* 푸시에 의존하지 않는다. iOS는 QR로 진입한 탭에서 웹 푸시를 받을 수 없다. 주문 알림은 알림톡을 주 경로로 한다.
* PWA 설치를 강제하지 않는다. iOS 독립 실행 모드에서 외부 인증·결제 복귀 후 화면이 멈추는 문제가 보고되어 있다.
* 주문 상태를 서버에 둔다. 브라우저는 7일 미사용 시 로컬 저장소를 삭제한다.
* QR에 매장 외부 접근 차단을 넣는다. QR만 있으면 매장 밖에서도 주문할 수 있다는 점이 약점으로 지적된다.

### 외부 POS 연동

* 얇은 웹훅과 전체 조회, 백업 폴링을 조합한다. Toast가 이 조합을 권장 방식으로 문서화했다. 웹훅은 변경됨 신호만 보내고 상세는 조회하게 한다.
* 품절과 일시중지는 메뉴 전체 동기화와 분리한다.
* 웹훅은 이벤트 식별자로 멱등 처리하고 2xx를 먼저 응답한 뒤 비동기로 처리한다.
* 매장 식별자를 단독 매칭 키로 쓰지 않는다. Uber Eats는 위치 정보로 검증한 뒤 활성화하게 한다.
* 메뉴 마스터의 단일 소유자를 못 박는다.

### 인증·권한

* 자체 계정과 역할 기반 권한, 조직 계층 범위 제한을 쓴다.
* 본사 관리자 등 특수 계정은 최소로 부여하고 별도 식별해 통제한다.
* 외부에서 어드민에 접속하는 경로에 IP 제한과 2차 인증을 적용한다. 개인정보의 안전성 확보조치 기준이 요구한다.
* 로그인 실패 횟수 제한과 계정 잠금을 넣는다.
* 접속기록은 계정, 일시, 접속지, 처리한 정보주체, 수행업무를 남기고 1년 이상 보관하며 월 1회 점검한다.
* SSO는 넣지 않는다. SSO 수요는 자체 인증 기반을 가진 기업 구매자가 조달 요건으로 요구할 때 발생한다.

## 3. 연동 구조

```text
                       본사 ERP (단일 애플리케이션)
                       행사 > 상권 > 직영·가맹 매장 > 카테고리 > 메뉴
                         │
         ┌───────────────┼───────────────┬───────────────┐
      api             admin           batch           worker
         │               │               │               │
         ▼               ▼               ▼               ▼
   주문 채널        내부 어드민       야간 집계        단말 이벤트
                   가맹 어드민       집계 테이블

ERP → 외부 POS  (매장 정보, 메뉴 마스터)
  변경 통지(웹훅): 매장 식별자 + 변경 시각만 전송      … 변경 즉시
  전체 조회:      외부 POS가 메뉴 전체를 다시 조회     … 통지 수신 시
  백업 폴링:      최종 변경 시각 조회                 … 30분 주기
  품절·일시중지:  항목 단위 별도 경로                 … 실시간
  인증: 클라이언트 자격증명, 매장 범위는 헤더 지정
  멱등: 이벤트 식별자. 2xx 선응답 후 비동기 처리

웹앱 (모바일 웹)
  고객 ─QR·링크→ 모바일 브라우저 → ERP api
   1) 매장·메뉴 조회
   2) 주문 생성 → 서버가 주문번호와 금액 저장
   3) PG 결제창 호출 (모바일은 리다이렉트)
       └→ 카드사 앱 ─복귀→ 복귀 주소
   4) 서버가 금액 검증 후 승인 호출  … 인증 후 10분 내, 멱등키, 타임아웃 시 망취소
   5) 주문 확정 → 매장 접수
   6) 알림톡 발송 (실패 시 문자 대체)
   ※ iOS 탭에서는 웹 푸시 불가

키오스크 (매장 설치)
  ERP api ─메뉴·가격 마스터→ 키오스크
     반영 트리거: 유휴 시간 + 결제 시점 체크
  키오스크 ─시리얼→ 카드리더기
     VAN 에이전트 또는 VAN 조회 API → VAN 센터 → 카드사
     승인 / 취소 / 망취소   … 온라인 실시간 필수
     네트워크 단절 시 카드 승인 불가
  키오스크 ─주문·승인 결과→ ERP api  (네트워크 복구 대기 큐 필요)
  관리 채널: 원격 업데이트 배포, 상태 모니터링
  네트워크: 유선 + 이동통신 라우터 이중화

결제 데이터 통합
  플랫폼 결제 식별자        ← 최상위 키, 모든 채널 공통
   ├ 승인번호               ← PG·VAN 공통
   ├ 거래 키                ← PG 전용
   └ VAN사·매입사·거래일련번호 ← VAN 전용
  매출 집계: PG와 VAN 통합 가능
  정산: 통합 불가. VAN 대금은 카드사에서 가맹점으로 직접 지급
```

## 4. 단계별 적용

| 단계 | 애플리케이션 | 데이터 | 인프라 | 외부 연동 | 규제·운영 |
| --- | --- | --- | --- | --- | --- |
| 1 내부 어드민 | 단일 앱, 어드민 실행 단위 | PostgreSQL 단일, 다중 가용영역 | 컨테이너 서비스 1개, 로드밸런서, 이미지 저장소, 모니터링 | 없음 | 관리자 IP 제한, 2차 인증, 접속기록 1년 보관과 월 1회 점검, 권한 최소·차등 부여 |
| 2 가맹 어드민 | 어드민 유지, 역할과 조직 범위 제한 추가 | 동일 DB. 조직 계층 기준 행 범위 제한 | 동일. 세션 저장소 추가 | 없음 | 가맹 계정 등록·변경·말소 이력, 접근권한 주기 검토 |
| 3 하이브리드 웹앱 | 주문 API 실행 단위 신설, 배치 신설 | 주문·결제 테이블. 야간 집계 배치와 집계 테이블을 여기서 시작 | 컨테이너 서비스 2~3개, 정적 자원 배포, 캐시 | PG 1개사, 카카오 알림톡(딜러사 계약, 템플릿 사전심사) | 통신판매업 신고, 거래기록 5년 보존, 계약 구조에 따른 PG업 등록 여부 사전 검토 |
| 4 키오스크 | 워커 실행 단위 신설 | 단말 상태·동기화 이력 | 메시지 큐, 단말 모니터링, 원격 업데이트 배포 채널 | VAN 연동, 매장별 VAN 계약 | 키오스크 접근성 의무, 등록 단말기 사용, 매장 네트워크 이중화 |
| 병행 외부 POS | 주문 API에 외부 채널 엔드포인트 추가 | 메뉴 변경 시각 관리 | 기존 인프라 재사용 | 웹훅 발송, 조회 API, 백업 폴링 | 연동 상대별 계약 |
| 이후 통계 확장 | | 읽기 전용 복제본, 필요 시 분석 저장소 | | | |

판단 기준은 다음과 같다. 3단계까지는 큐가 없어도 된다. 4단계에서 매장 네트워크가 제각각이고 행사 트래픽이 몰리므로 큐가 필요해진다. 읽기 전용 복제본은 통계 조회가 주문 처리에 영향을 주기 시작할 때 붙인다. 분석 저장소는 분석 쿼리가 운영 커밋을 지연시킬 때 검토한다.

## 5. 확인 필요

규제·계약

1. 본사가 가맹점 대금을 수취·정산하는지 여부. PG업 등록 대상 여부가 여기서 갈린다. 법무 확인이 선행되어야 한다.
2. 포인트·기프트 기능 도입 여부. 도입 시 선불업 등록 기준 검토가 필요하다.
3. 장애인차별금지법 시행령의 모바일앱 정의에 모바일 웹이 포함되는지.
4. 테이블오더형 소형제품의 정확한 정의와 검증기준 표준 번호.

결제

5. 각 PG사의 멱등키 헤더 지원 여부.
6. PG와 VAN을 하나로 추상화하는 상용 수단이 없다. 자체 구현이 필요할 가능성이 높다.
7. VAN 3~4일, PG 익일이라는 정산 주기의 공식 근거. 업체 블로그 출처만 확보했다.
8. 키오스크가 네트워크 단절 시 주문만 로컬에 쌓고 결제를 막는지 여부. 벤더 공개 문서에 없다.

연동

9. 오케이포스 프랜차이즈 ERP 연동 표준 API의 실제 스펙. 존재만 확인되고 내용은 비공개다.
10. 배달 플랫폼의 공개 API 존재 여부.
11. 외부 POS가 ERP로 매출을 역전송하는 국내 표준 방식.

단말·운영

12. 국내 테이블오더·키오스크 제품이 매장 주문 접수를 실시간으로 무엇으로 전달하는지. 벤더 문서에 기술 상세가 없다.
13. 국내 F&B·프랜차이즈 도메인의 엔지니어링 자료가 없다. 가장 가까운 대체 근거가 올리브영이다.
14. 국내 가맹점주 대상 어드민의 실제 로그인 방식.

# 보완 조사 (2026-09-03)

## A. 정정 — 어드민 2차 인증은 권고가 아니라 법적 의무다

개인정보의 안전성 확보조치 기준 제6조 제2항은 개인정보처리시스템에 대한 정당한 접근 권한을 가진 자가 정보통신망을 통해 외부에서 접속하려는 경우 인증서, 보안토큰, 일회용 비밀번호 등 안전한 인증수단을 적용하도록 요구한다. 같은 조 제1항은 IP 주소에 의한 접속 권한 제한과 접속 IP 분석을 통한 유출 시도 탐지·대응을 함께 의무화한다.

* 적용 대상은 정당한 접근 권한을 가진 자이며 정보주체만 제외된다. 본사 직원, 슈퍼바이저, 가맹점주가 모두 포함된다.
* 계정과 비밀번호만으로는 충족되지 않는다.
* 단서가 실무상 분기점이다. 어드민이 이용자 개인정보를 다루지 않으면 가상사설망 등 안전한 접속수단으로 갈음할 수 있다. 어드민 화면에 주문자 연락처와 주소를 노출할지 여부가 인증 요건 강도를 결정한다.
* 제1항 제2호는 로그 적재만으로 부족하고 분석과 대응 절차를 요구한다.

## B. 추가 — 대행 로그인은 국내 표준 요구사항이다

오케이포스는 접속 주체를 대리점, 본사, 가맹점 3단으로 나누고, 상위 조직이 자기 계정으로 로그인한 뒤 매장 계정에 대신 접속하는 기능을 제공한다. 권한은 항목 단위로 갈린다. 사업자 기본 정보는 가맹점과 상위 조직 모두 수정할 수 있으나 VAN, 단말 계약번호, 사업자번호 등 시스템 설정은 상위 조직에서만 변경할 수 있다.

본사가 가맹 어드민 화면을 대신 보는 기능은 예외가 아니라 기본 요구사항이다. 다만 접속기록 기준상 계정, 접속일시, 접속지, 처리한 정보주체, 수행업무를 남겨야 하므로 대행 접속은 실제 조작자와 대상 계정을 함께 기록하도록 별도 설계해야 한다.

## C. 추가 — 메뉴 마스터 설계 원칙 네 가지

1. **마스터를 하나로 못 박는다.** Square는 연동 시작 전에 어느 쪽이 기준인지 먼저 정하라고 요구하고 양방향 동기화를 위험한 작업으로 경고한다. 동시성, 병합, 중복, 삭제, 가격 무결성이 이유다.
2. **본사 마스터 상속과 매장 예외를 데이터 구조로 만든다.** Deliverect는 기준 매장을 두고 다른 매장이 그 상품을 참조하게 설정하면 매장별로 따로 배포하지 않는다. 참조하지 않는 매장은 자기 소스에서 가져온다.
3. **마스터 데이터와 채널 표현을 분리한다.** Deliverect에서 상품의 기준은 POS이고 메뉴 조립은 별도에서 한다. 완성된 메뉴는 보통 상품의 부분집합이다. 상품을 다시 동기화해도 메뉴 단계의 설정을 덮어쓰지 않는다. Olo도 같은 메뉴에 대해 채널별 가격을 따로 설정해 배포한다. ERP의 메뉴 마스터와 채널별 노출을 같은 구조로 다루면 안 된다.
4. **품절은 참·거짓이 아니라 시한값이다.** Uber Eats는 중지 종료 시각을 넣고, 과거 시각이거나 비어 있으면 자동으로 판매 가능으로 돌아온다. 사유와 적용 범위를 함께 지정한다. 언제까지 중지로 모델링하면 매장이 해제를 잊는 문제가 사라진다.

층위도 나눈다. 상품 단위 중지, 매장 단위 상태(정상·지연·일시중지), 매장 폐점을 각각 다르게 다룬다.

## D. 추가 — 외부 연동 인증·제한 관행

* Uber Eats는 인증 방식을 용도별로 나눈다. 일반 운영은 클라이언트 자격증명, 매장 최초 활성화는 판매자 동의 기반이다. 범위도 매장·메뉴, 주문, 리포트로 분리한다.
* 토큰 유효기간 30일, 발급 요청은 시간당 100회로 제한된다. 초과하면 가장 오래된 토큰이 무효화된다. 공식 권고는 토큰을 만료까지 캐시해 재사용하는 것이다. 가맹점 수가 많은 구조에서 요청마다 발급하면 바로 걸린다.
* 전체 메뉴를 최소 1회 올려야 개별 항목 갱신이 실패하지 않는다.
* Square는 날짜 기반 버전 관리를 쓴다. 요청 헤더로 개별 재정의해 신규 버전을 먼저 시험한 뒤 올린다. 다수 가맹점과 다수 POS사가 동시에 붙는 구조에서 점진적 전환에 유리하다.
* Square 웹훅은 카탈로그 버전 변경 하나뿐이고 페이로드에 변경 내용이 없다. 일괄 반영은 배치 전체에 알림 1건이다. 웹훅으로 알리고 조회로 받아가는 방식이 표준이다.
* Olo는 변경을 감지해 파트너용 신규 메뉴 파일을 만들고 알림을 보낸다. 대시보드 변경은 수 분 내 반영되고 최초 생성은 약 30분이다.
* 외부 시스템 식별자는 별도 속성에 저장해 매핑을 관리하라는 것이 Square 권고다.

## E. 추가 — 권한 모델 선택의 근거

AWS 문서는 역할 기반 권한의 실패 지점을 이 도메인 형태로 지적한다. 사용자가 새 리소스를 추가할 때마다 접근을 허용하도록 정책을 갱신해야 한다는 점이다. 프랜차이즈는 매장이 계속 늘어난다. 데이터 범위를 역할로 표현하면 매장이 생길 때마다 정책을 손봐야 한다.

* 인가 로직을 애플리케이션 코드에서 분리한다. 코드에 박으면 실수나 악의로 교차 접근이 나고 감사가 어렵다.
* 정책 관리, 정책 판단, 정책 집행을 나누고 집행 지점을 각 진입점에 붙인다.
* 가장 중요한 구분은 다음이다. 사용자가 인증됐다는 사실이 격리를 달성했다는 뜻이 아니다. 인증되고 인가된 상태로도 다른 조직의 자원에 접근할 수 있다. 본사 관리자 역할 부여와 본사 A 데이터만 보임은 별개의 통제이므로 반드시 분리해 설계한다.

DB 행 수준 보안을 쓸 경우 주의할 점이다. 정책이 없으면 기본 전면 거부다. 허용 정책은 합집합으로, 제한 정책은 교집합으로 결합되므로 조직 격리는 제한 정책으로 걸어야 한다. 슈퍼유저와 우회 권한 보유 역할은 무조건 우회하며 막을 수 없고, 테이블 소유자도 기본적으로 우회한다. 애플리케이션 접속 계정이 테이블 소유자면 무력화된다. 외래키와 유일성 제약 검사는 이 통제를 우회한다.

## F. 정정 — 국내 연동은 공개 API가 아니다

배달 플랫폼 3사 모두 공개 개발자 포털이 확인되지 않는다. 파트너센터 신청과 승인 기반이다. 유니온포스의 주소는 포털 로그인 화면으로 넘어간다. 오케이포스만 프랜차이즈 ERP 연동 표준 API 제공을 공개적으로 표방하나 해당 페이지 본문이 이미지라 명세를 추출할 수 없고, 상품·단가 마스터 배포 프로토콜 문서 항목은 존재하지 않는다는 답을 받았다.

국내 POS 연동 사양은 계약 후 개별 제공받는 것이 관행이다. 기획 단계에서는 우리 쪽 제공 규격을 표준으로 먼저 정의하고 상대 POS사별 어댑터를 두는 구조가 현실적이다.

## G. 정정 — 가맹점주 SSO는 근거가 없다

조사 결과 반대 방향의 정황만 확인된다. 오케이포스는 자체 계정과 대행 로그인, 유니온포스는 자체 계정이다. 가맹점주는 본사 소속 직원이 아니라 독립 사업자이므로 자체 인증 기반이 없다. 연동의 전제가 성립하지 않는다.

인증을 이원화한다. 본사 임직원은 사내 인증 기반 연동이 가능하고, 가맹점주와 매장 담당자는 자체 계정과 안전한 인증수단을 쓴다. 다만 이 이원화를 뒷받침하는 국내 공개 사례는 확보하지 못했다.

## 보완 확인 필요

* 어드민이 주문자 개인정보를 노출하는지 여부. 안전성 확보조치 기준 제6조 제2항 단서 적용 여부가 여기서 갈린다.
* 오케이포스 프랜차이즈 ERP 표준 API의 실제 명세. 제휴 문의로만 확인할 수 있다.
* 본사가 가맹점 단말로 상품·단가 마스터를 배포하는 프로토콜. 공개 문서에 항목 자체가 없다.
* 배달 플랫폼 연동 신청 경로의 공식 근거.
