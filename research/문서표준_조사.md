# 조사 자료 — 문서 형식 표준

조사일 2026-09-04. 기획 문서의 구성 항목과 표기 규칙을 표준에 맞추기 위한 근거다. 적용 결정은 `CLAUDE.md`의 문서 표준 절에 있다.

## 1. 표준 목록

| 표준 | 제목 | 범위 | 우리 문서 적용 |
| --- | --- | --- | --- |
| ISO/IEC/IEEE 29148:2018 | 요구사항 공학 | 요구사항 프로세스와 4종 명세서 | 기능 명세, 기획 검토, 요구사항 표기, 추적성 |
| ISO 5807:1985 | 순서도 기호와 규약 | 기호 25종과 작도 규약 | Flow Chart 전체 |
| ISO/IEC 19510:2013 | 업무 프로세스 표기 | 업무 흐름 표기법 | 참고 |
| OMG UML 2.5.1 | 통합 모델링 언어 | 활동 다이어그램 등 | 참고 |
| ISO/IEC/IEEE 42010:2022 | 아키텍처 기술 | 아키텍처 기술서 필수 구성 | 서비스 구조 |
| ISO/IEC/IEEE 15289:2019 | 생명주기 정보항목 내용 | 전 문서의 공통 내용 | 8종 문서 공통 |

ISO 5807은 현재 유효하다. 2019년 확인을 거쳤고 대체 표준이 없다. 한국은 KS X ISO 5807로 채택했다.

ISO/IEC/IEEE 42010은 2011년판이 폐지되고 2022년판이 현행이다.

IA와 Wireframe의 문서 구성을 규정한 국제 표준은 확인되지 않았다.

## 2. 순서도 기호 (ISO 5807 조항 9)

| 기호 | 형태 | 의미 |
| --- | --- | --- |
| 데이터 | 평행사변형 | 데이터를 나타낸다. 매체는 규정하지 않는다 |
| 저장 데이터 | 좌측 곡선 사각형 | 처리에 적합한 형태로 저장된 데이터 |
| 처리 | 직사각형 | 모든 종류의 처리 기능. 값·형태·위치를 바꾸거나 흐름 방향 하나를 결정하는 것을 포함한다 |
| 정의된 처리 | 양측 이중선 직사각형 | 다른 곳에 명세된 처리. 서브루틴이나 모듈 |
| 수작업 | 하변이 짧은 사다리꼴 | 사람이 수행하는 처리 |
| 준비 | 육각형 | 후속 활동에 영향을 주는 명령의 수정 |
| 판단 | 마름모 | 판단 또는 분기. 입구는 하나. 출구는 여럿일 수 있으나 조건 평가 후 하나만 활성화된다 |
| 병렬 방식 | 상하 이중 수평선 | 둘 이상 병렬 연산의 동기화 |
| 루프 한계 | 모서리 절단 사각형 두 개 | 루프의 시작과 끝. 두 부분은 같은 식별자를 가진다 |
| 선 | 실선 | 데이터 또는 제어의 흐름 |
| 파선 | 파선 | 둘 이상 기호 간의 택일 관계. 주석 영역을 둘러쌀 때도 쓴다 |
| 결합자 | 작은 원 | 같은 도표 내 다른 부분으로의 출구 또는 입구. 대응하는 결합자는 같은 이름을 가진다 |
| 단자 | 양끝 둥근 사각형 | 외부 환경으로의 출구 또는 입구. 흐름의 시작과 종료 |
| 주석 | 파선으로 연결된 대괄호 | 설명이나 주를 덧붙인다 |
| 생략 | 점 세 개 | 기호의 종류와 개수를 정의할 필요가 없을 때의 생략 |

기타 기호로 내부 기억장치, 순차접근 기억장치, 직접접근 기억장치, 서류, 수동 입력, 카드, 천공 테이프, 표시, 제어 이동, 통신 연결이 있다.

ISO 5807에는 오각형 형태의 페이지 넘김 기호가 없다. 특수 기호는 결합자, 단자, 주석, 생략 네 가지뿐이다. 페이지 넘김은 결합자에 주석을 붙여 표시한다.

## 3. 작도 규약 (ISO 5807 조항 10)

### 기호

* 기호에 공간을 고르게 배분한다. 긴 선을 최소화한다.
* 표준이 제시한 형태를 따른다. 각도 등 형태에 영향을 주는 요소를 바꾸지 않는다. 크기는 통일한다.
* 기호 안 설명 문자는 최소한만 쓴다. 흐름 방향과 무관하게 왼쪽에서 오른쪽, 위에서 아래로 쓴다.
* 기호 식별자는 좌측 상단에, 설명자는 우측 상단에 쓴다.
* 처리나 데이터 기호 안쪽 상단에 가로선을 그으면 다른 곳에 더 상세한 표현이 있다는 뜻이다.

### 흐름선

* 표준 흐름 방향은 왼쪽에서 오른쪽, 위에서 아래다.
* 표준 방향이 아니면 화살촉을 반드시 붙인다. 명확성을 위해 언제든 붙일 수 있다.
* 교차는 가능하나 피한다. 교차한 선 사이에는 논리적 관계가 없다.
* 합류 시 연결점을 어긋나게 해 명확성을 높인다.
* 흐름선은 기호의 좌변이나 상단으로 들어가고 우변이나 하단으로 나간다. 모두 기호 중심을 향한다.

### 분기

* 다중 출구는 두 방법 중 하나로 표기한다. 기호에서 여러 흐름선을 직접 인출하거나, 한 선을 인출한 뒤 여러 갈래로 나눈다.
* 각 출구에 그것이 나타내는 논리 경로를 반영하는 조건 값을 표기한다.

## 4. 요구사항 작성 규칙 (ISO/IEC/IEEE 29148)

### 개별 요구사항의 특성 (5.2.5)

필요성, 적절성, 명확성, 완전성, 단일성, 실현 가능성, 검증 가능성, 정확성, 형식 준수 아홉 가지를 갖춰야 한다.

* 명확성은 오직 한 가지로만 해석되도록 진술하는 것이다.
* 단일성은 하나의 역량이나 특성만 진술하는 것이다.
* 검증 가능성은 실현을 입증할 수 있게 구조화하는 것이다. 측정 가능할 때 향상된다.
* 적절성은 아키텍처와 설계에 불필요한 제약을 두지 않는 것이다.

### 요구사항 집합의 특성 (5.2.6)

완전성, 일관성, 실현 가능성, 이해 가능성, 확인 가능성 다섯 가지다. 미정 항목이 하나라도 남아 있으면 집합을 완전하다고 보지 않는다.

### 문장 규칙 (5.2.4)

| 표현 | 성격 |
| --- | --- |
| shall | 의무. 요구사항에 쓴다 |
| should | 권장. 요구사항이 아니다 |
| may | 허용 |
| will | 사실이나 미래 선언 |
| must | 쓰지 않는다. 요구사항으로 오해될 수 있다 |

추가 규칙은 다음과 같다. 긍정문을 쓰고 부정 요구사항을 피한다. 능동태를 쓴다. 요구사항 문장은 주어와 동사를 포함하고, 주체와 무엇을 해야 하는지를 진술한다.

### 금지 표현 (5.2.7)

무엇이 필요한지를 적고 어떻게 하는지는 적지 않는다. 모호하고 일반적인 용어를 피한다.

| 유형 | 예 |
| --- | --- |
| 최상급 | 최고의, 가장 |
| 주관적 표현 | 사용자 친화적인, 쓰기 쉬운, 비용 효과적인 |
| 모호한 대명사 | 그것, 이것 |
| 모호한 부사·형용사 | 거의 항상, 상당한, 최소한의 |
| 접속 표현 | 또는, 그리고 또는. 이 표현을 만나면 요구사항을 분리한다 |
| 개방형 표현 | 지원을 제공한다, 이에 한정되지 않는다 |
| 비교 구문 | 보다 나은, 더 높은 품질의 |
| 빠져나갈 구멍 | 가능하면, 적절히, 해당되는 경우 |
| 전체성 함의 | 모든, 항상, 결코, 모두 |
| 불완전한 참조 | 날짜나 버전 번호를 적지 않음 |

### 식별자 (5.2.8.2)

각 요구사항은 고유하게 식별한다. 한 번 부여한 식별자는 요구사항 내용이 바뀌어도 변경하지 않는다. 요구사항이 삭제되어도 재사용하지 않는다.

운영 정책과 규칙은 고유하게 이름을 붙이고 번호를 매겨야 한다. 시스템 프로세스와 운영 시나리오도 같다.

### 추적성 (6.4.3.5)

요구사항은 다음으로 추적할 수 있어야 한다.

| 방향 | 대상 |
| --- | --- |
| 아래 | 하위 요구사항. 할당으로 달성한다 |
| 옆 | 아키텍처, 그 요구사항을 구현하는 시스템 요소 |
| 옆 | 그것을 충족하는 검증과 시험 항목 |
| 위 | 파생된 상위 요구사항, 또는 변환된 이해관계자 필요 |

인터페이스 요구사항도 추적성에 포함한다. 양방향 추적은 적용 범위 분석, 준수 분석, 영향 분석의 기반이 된다.

## 5. 요구사항 명세서 구성 (29148 9.6)

절 번호와 순서는 규범이 아니다. 내용 항목만 규범이다.

주요 항목은 목적, 범위, 제품 관점, 인터페이스, 제품 기능, 사용자 특성, 한계, 전제와 종속, 요구사항 배분, 명시된 요구사항, 외부 인터페이스, 기능, 사용성, 성능, 논리적 데이터베이스, 설계 제약, 표준 준수, 소프트웨어 시스템 속성, 검증, 보조 정보다.

명세서는 네 종류로 나뉜다.

| 구분 | 관점 | 내용 |
| --- | --- | --- |
| 사업 요구사항 명세 | 경영 관리 | 사업 목적, 범위, 목표, 업무 프로세스, 업무 규칙 |
| 이해관계자 요구사항 명세 | 업무 운영 | 이해관계자 목적과 목록, 사업 환경, 시스템 프로세스, 운영 정책과 규칙, 운영 개념, 운영 시나리오 |
| 시스템 요구사항 명세 | 도메인·기술 | 시스템 목적, 범위, 기능, 사용성, 성능, 인터페이스, 운영, 모드와 상태, 보안, 정보관리 |
| 소프트웨어 요구사항 명세 | 소프트웨어 제품 | 위 주요 항목 |

## 6. 문서 공통 항목 (15289 조항 7, 29148 9.2)

각 정보항목은 아래 공통 내용을 필수로 포함한다.

| 항목 | 적용 문서 유형 |
| --- | --- |
| 발행일 및 상태 | 전부 |
| 범위 | 전부 |
| 발행 조직 | 전부 |
| 참조 문서 | 전부 |
| 승인 권한 | 계획, 정책, 절차, 명세 |
| 대상 독자 | 계획, 보고 |
| 본문 | 전부 |
| 용어집 | 전부 |
| 변경 이력 | 전부 |

29148 9.2가 추가로 요구하는 것은 다음과 같다. 표제와 개정 통지로 문서를 고유하게 식별한다. 개정 정보에는 프로젝트명, 버전 번호, 배포일, 승인 서명, 현재 버전에서 변경된 절 목록, 이전 버전의 번호와 배포일을 담을 수 있다. 목차와 그림 목차, 표 목차를 둔다. 참조 문서는 제목, 번호, 날짜, 발행 기관, 입수처로 식별하고 준수용과 참고용으로 나눈다.

버전 번호 체계를 규정한 표준은 없다. 버전 번호를 요구할 뿐 형식은 자유다.

## 7. 아키텍처 기술 (42010)

아키텍처 기술서에 포함해야 하는 것은 다음과 같다.

| 항목 | 내용 |
| --- | --- |
| 식별과 개요 | 문서 식별 정보 |
| 이해관계자와 관심사 | 누가 무엇에 관심을 갖는지 |
| 관점 | 사용한 각 관점의 정의 |
| 뷰 | 관점마다 하나의 뷰 |
| 모델 | 뷰를 구성하는 모델. 버전 식별을 포함한다 |
| 대응 관계 | 요소 간 관계와 규칙 |
| 근거 | 각 관점의 근거, 핵심 결정의 근거, 검토한 대안과 선택 이유 |

결정을 기록할 때 고려할 것은 고유 식별, 결정 진술, 관련 관심사 연결, 소유자, 영향받는 요소 연결, 근거 연결, 제약과 전제, 검토한 대안과 결과, 시점이다.

모든 결정을 기록하는 것은 실용적이지 않다. 핵심 결정을 선별한다. 선별 기준은 아키텍처적으로 유의미한 요구사항 관련, 큰 노력 투입, 다수 이해관계자 영향, 복잡한 추론 필요, 변경 비용이 큼이다.

## 8. 업무 표기법 선택

표준이 무엇을 쓸지 지정하지 않는다. 확인된 사실은 다음과 같다.

* 업무 프로세스 표기는 BPMN이 자기 범위로 선언한 영역이다. 조직 모델, 기능 분해, 데이터 모델, 업무 규칙 모델은 범위 밖이라고 명시한다.
* 요구사항 문서 안의 시스템 동작에는 소프트웨어 공학 지식체계의 요구사항 영역이 UML 활동 다이어그램을 지목한다.
* 순서도는 여전히 유효한 표준이며 소프트웨어 공학 지식체계의 설계 영역이 활동 다이어그램, 데이터 흐름도, 결정표, 상태도와 동등한 표기로 나열한다.

## 9. 확인하지 못한 항목

1. ISO 5807 기호의 정확한 도형. 미리보기와 동일채택본 모두 도해가 이미지라 판독하지 못했다. 형태 설명은 통용되는 작도를 적은 것이다.
2. 42010:2022 조항 6·7·8의 의무 조항 본문. 유료로 확보하지 못했다. 조항 번호와 제목만 확인했다.
3. 15289 조항 7 항목명의 영문 원표기. 동일채택 국가표준에서 역번역했다.
4. 29148의 요구사항 문장 구문 도해. 벡터 도해라 판독하지 못했다.
5. IA와 화면설계서의 문서 구성을 규정한 국제 표준. 찾지 못했다.
