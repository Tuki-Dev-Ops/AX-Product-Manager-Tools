# 조사 자료 — 모바일 스마트오더

조사일 2026-09-03. 02 기획 검토의 근거 자료다. 이 파일은 조사 원본이며, 기획 판단은 `docs/02_기획검토.md`에 정리한다.

조사 대상: 스타벅스 사이렌오더, 배민오더(QR오더), 카카오톡 주문하기, 네이버 주문, 페이히어 스마트오더, 티오더·토스오더 QR오더, 해피오더. 결제는 토스페이먼츠, 나이스페이먼츠, KG이니시스, 포트원 문서.

보편성은 위 조사 대상 기준이다.

## 2. 주문 흐름

```text
진입
 ├─ QR 스캔 → 매장·테이블 자동 확정, 매장 선택 생략
 └─ 웹 링크
     └─ 위치 권한
         ├─ 허용 → 인근 매장 목록(거리순)
         └─ 거부 → 매장명 검색

매장 확정 후 게이트
 ├─ 영업시간 외 → 주문 불가, 메뉴 열람만 허용
 ├─ 주문 가능 시간 외 → 주문 불가
 ├─ 매장 반경 밖 → 주문 불가
 └─ 정상 → 수령 방식 선택

메뉴 조회
 ├─ 시간·요일별 메뉴판 분기
 ├─ 품절 메뉴 → 담기 차단
 └─ 매장별 가격 적용

옵션 선택
 ├─ 필수 옵션 미선택 → 담기 차단
 ├─ 옵션 품절 → 해당 옵션만 비활성
 └─ 합계 실시간 재계산

장바구니
 ├─ 다른 매장 상품 존재 → 초기화 확인
 └─ 담긴 후 품절 발생 → 주문서 진입 시 재검증

주문서 확인
 ├─ 회원 → 계정 정보 자동 입력
 ├─ 비회원 → 이름·휴대폰번호 입력
 ├─ 쿠폰·포인트 적용 → 최종 금액 확정
 └─ 서버에 주문번호·최종금액 임시 저장 (위변조 검증 기준값)

결제
 ├─ 선결제 → PG 결제
 └─ 만나서 결제 → PG 미경유, 주문만 전송

주문 접수
 ├─ 매장 수락 → 주문 확정
 ├─ 매장 거절 → 주문 취소 + 결제 전액 취소 + 알림
 └─ 제한 시간 미응답 → 자동 취소 + 결제 취소 + 알림

준비
 접수 → 제조 중 → 준비 완료 → 알림 발송

픽업
 ├─ 주문번호 호출로 수령
 └─ 수령 기한 초과 → 매장 정책 처리
```

## 3. PG 결제 처리 순서

VAN은 카드 단말에서 카드사로 승인을 중계하는 단일 단계다. PG는 인증과 승인을 분리하고 그 사이에 가맹점 서버의 금액 검증을 둔다.

1. 주문 사전 등록. 서버가 주문번호와 최종 결제금액을 저장한다. 이 값이 검증 기준값이다.
2. 결제 요청. 클라이언트가 PG 결제창을 연다. 성공·실패 복귀 주소를 함께 전달한다.
3. 결제수단 인증. 카드사가 구매자를 인증한다. 이 단계에서 외부 결제 앱이 호출될 수 있다.
4. 인증 결과 수신. 모바일 웹은 리다이렉트로 받는다. 토스페이먼츠는 쿼리 파라미터, 나이스페이먼츠는 form POST, 포트원은 쿼리스트링으로 전달한다.
5. 금액 위변조 검증. 1에서 저장한 값과 4에서 받은 값을 서버에서 비교한다. 이 검증이 없으면 클라이언트 조작이 가능하다.
6. 결제 승인 요청. 검증 통과 시에만 서버가 승인 API를 호출한다. 이 시점에 실제 차감이 일어난다.
7. 멱등키 부여. 재시도 시 중복 승인을 막는다. 처리 중 동일 키 재요청은 409로 반환된다.
8. 주문 확정. 승인 상태 확인 후 주문을 확정한다.
9. 웹훅 수신. 결제 상태 변경을 별도로 받아 정합성을 맞춘다. 전송 실패 시 최대 7회 재전송한다.

### 취소·환불

| 항목 | 처리 |
| --- | --- |
| 전액 취소 | 결제 키와 사유로 취소 API 호출. 멱등키로 중복 취소 방지 |
| 부분 취소 | 취소 금액 지정. 미입력 시 전액 취소 |
| 카드 | 매입 전 즉시. 매입 후·부분 취소는 3~4일 |
| 계좌이체 | 180일 이내, 실시간 |
| 가상계좌 | 환불계좌 필수, 약 2일. 입금 전 부분 취소 불가 |

F&B 스마트오더에서는 카드와 간편결제가 실질 표준이다. 가상계좌와 휴대폰결제는 즉시 픽업 특성과 맞지 않아 일반적으로 쓰지 않는다.

## 4. 회원·비회원

| 항목 | 실태 | 보편성 |
| --- | --- | --- |
| 플랫폼 계정 기반 | 카카오·네이버·배민 등 플랫폼 내장형은 로그인 상태를 전제한다 | 대부분 |
| 앱 설치 불필요 | QR·링크 접근형은 앱 없이 주문한다 | 대부분 |
| 소셜 로그인 | 자체 웹앱은 카카오·네이버 간편로그인이 일반적이다 | 대부분 |
| 비회원 주문 | 자체 웹앱·QR오더에서 관찰된다. F&B 한정 공식 근거는 확보하지 못했다 | 일부 |
| 주문 내역 조회 | 회원은 계정 내, 비회원은 휴대폰번호·주문번호 조합 | 대부분 / 일부 |

## 5. 하이브리드 웹앱 제약

| 항목 | 제약 |
| --- | --- |
| 푸시 알림 (iOS) | iOS 16.4 이상에서 홈 화면에 추가한 경우에만 동작한다. Safari 탭 상태에서는 수신할 수 없다 |
| 푸시 대안 | 실무에서는 카카오 알림톡으로 접수·준비완료를 통지한다 |
| 결제 앱 복귀 | 순수 모바일 웹은 복귀 주소 리다이렉트로만 결과를 받는다. 세션이 복원되지 않으면 결과가 유실된다. 서버 결제 조회와 웹훅 이중화가 필요하다 |
| 앱 미설치 | Android는 intent 스킴의 패키지 정보로 스토어 이동을 처리한다. iOS는 스킴 실패를 감지해 처리한다 |
| 카메라(QR) | HTTPS 필수. 카카오톡 인앱브라우저(Android)에서 카메라 접근이 거부되는 사례가 보고되었다 |
| QR 진입 방식 | OS 기본 카메라로 QR을 촬영해 링크로 진입하는 것이 표준이다. 웹앱 내부 스캐너는 필수가 아니다 |

## 6. 법정 표시 의무

### 원산지 표시 (농수산물 원산지 표시법)

* 대상: 일반음식점, 휴게음식점, 위탁급식소, 집단급식소. 사실상 모든 F&B.
* 품목: 쇠고기, 돼지고기, 닭고기, 오리고기, 양고기, 쌀, 배추김치, 콩, 살아있는 수산물 등.
* 방법: 사용 중인 모든 메뉴판에 표시한다. 글자 크기는 메뉴 이름과 같거나 커야 한다. 배추김치는 원료 원산지를 병기한다.
* 위반 시 1천만원 이하 과태료.
* 시사점: 모바일 메뉴판도 메뉴판이다. 메뉴 정보에 원산지 항목이 필요하고, 메뉴명 대비 글자 크기 제약이 화면 요건이 된다.

### 알레르기 유발식품 표시 (어린이 식생활안전관리 특별법)

* 대상: 어린이 기호식품을 조리·판매하는 업소 중 가맹점 50개 이상.
* 대상 식품: 햄버거, 피자, 제과·제빵류, 아이스크림류 등.
* 표시 항목: 알레르기 유발 원재료명과 영양성분(열량, 당류, 단백질, 포화지방, 나트륨).
* 유발식품 목록: 알류, 우유, 메밀, 땅콩, 대두, 밀, 고등어, 게, 새우, 돼지고기, 복숭아, 토마토, 아황산류, 호두, 닭고기, 쇠고기, 오징어, 조개류, 잣.

## 7. 예외 처리

| 상황 | 처리 |
| --- | --- |
| 결제 승인 실패 | 실패 주소로 복귀. 주문 미확정 유지, 결제수단 재선택 유도 |
| 결제창 이탈 | 승인 API 미호출. 주문 생성 안 됨. 재시도 시 새 주문번호 발급 |
| 금액 위변조 감지 | 승인 API를 호출하지 않고 중단, 주문 실패 처리 |
| 매장 거절·미수락 | 주문 취소 + 결제 전액 취소 + 고객 알림 |
| 승인 성공 후 응답 유실 | 동일 멱등키로 재요청. 처리 중이면 409, 재조회 후 처리 |
| 중복 결제 | 주문번호 유일성과 멱등키로 차단. 결제 조회로 확인 후 신규 승인 미수행 |
| 리다이렉트 결과 유실 | 웹훅으로 상태 수신, 서버 결제 조회로 확정. 위조 검증 값 비교 |
| 영업 종료·주문 시간 외 | 게이트에서 차단, 메뉴 열람만 허용 |
| 품절 (담기 전) | 메뉴판에 즉시 반영, 선택 불가 |
| 품절 (담긴 후) | 주문서 진입·결제 직전 재검증에서 제거 또는 차단 |
| 픽업 미수령 | 매장 정책에 따라 처리 |

## 8. 조사 한계

1. 비회원 주문. 조사 대상 주요 서비스가 플랫폼 계정 기반이라 F&B 한정 공식 근거를 확보하지 못했다. 국내 커머스 일반의 비회원 조회 방식이 근거다.
2. 매장별 가격 차이. 매장 단위 메뉴·가격 관리 근거는 확보했으나, 동일 브랜드 내 매장별 가격 상이를 명시한 공식 문서는 찾지 못했다.
3. 픽업 시간 지정. 일부 서비스에서만 확인된다.
