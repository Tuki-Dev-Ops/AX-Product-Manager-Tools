## 2. 검토 사항

### R-1 연계 규격이 문서에 없다

07 기능 명세를 화면 단위로 작성했다. 목적, 대상, 처리, 조건, 예외, 연결 Flow를 갖췄다.

외부 연계 규격은 아직 없다. 결제대행사와 VAN사, 알림톡, 외부 POS의 요청과 응답 항목이 정의되지 않았다. 계약 후 상대가 제공하는 규격에 맞춰야 하므로 지금 확정할 수 없다. 계약 시 확인할 항목은 02 문서 2.7과 2.22에 있다.

### R-2 계정 발급 경로가 둘이다

상권을 등록하면서 담당 계정을 함께 발급한다. 시스템 > 관리자에서도 계정을 발급한다.

두 경로가 만드는 계정은 같다. 상권 등록에서는 역할이 가맹 관리자, 담당 범위가 그 상권으로 고정되고, 관리자 메뉴에서는 둘 다 고를 수 있다.

계정 정보 수정과 비밀번호 재설정, 사용 중지는 관리자 메뉴에서만 한다. 상권 화면에서는 읽기만 한다. 발급 경로는 둘이지만 관리 경로는 하나다.

상권 담당자가 여러 명인 경우는 관리자 메뉴에서 계정을 추가한다. 상권 등록에서 계정을 여러 개 만드는 화면은 두지 않는다. 상권 등록은 첫 담당자 한 명을 만드는 자리이고, 그 뒤의 증감은 계정 관리에서 다룬다.

### R-3 주문 흐름을 유사 서비스와 대조하고 반영했다

스타벅스 사이렌 오더, 토스오더 픽업주문, 배민스토어 픽업과 상태 흐름을 대조했다.
결제 승인 → 매장 접수 → 준비 → 완료 알림 → 수령의 뼈대와 접수 전에만 고객이 취소할 수 있는 규칙은 같다.
키오스크 주문을 결제와 동시에 접수 완료로 넣는 것도 맞다.

네 가지가 다르거나 빠져 있다.

| 항목 | 이전 | 확인된 기준 | 반영 |
| --- | --- | --- | --- |
| 미응답 제한 시간 | 1분 | 토스오더 5분, 배민스토어 15분 | 5분. 남은 시간을 행에 표시하고 1분 남으면 붉게 바꾼다 |
| 예상 준비 시간 | 화면에 표시만 있고 정하는 주체가 없다 | 스타벅스는 결제 전 안내, 배민은 접수 시 5~60분 지정 | 매장 정보의 기본값을 결제 전에 안내하고, 접수할 때 매장이 다시 고른다 |
| 미수령 주문 | 정의 없음 | 배민은 결제 24시간 뒤 자동 픽업완료 | 영업 종료 한 시간 뒤 배치가 수령 완료로 바꾸고 미수령으로 남긴다 (FL-146) |
| 거절 사유 | 받지 않는다 | 배민은 사유 선택, 품절이면 재고 0 연동 | 품절·재료 소진·마감·기타. 품절이면 그 메뉴를 품절로 바꾼다 (STR-ORDR-RJCT) |

스타벅스는 전 매장이 직영이라 거절이 없고 결제가 곧 접수다. 본 서비스는 행사장 가맹 매장이 운영해
재료 소진과 조기 마감이 잦다. 매장 수락 단계는 유지한다. 가져온 것은 시간을 다루는 방식이다.

접수 완료 후 1분간 고객이 취소할 수 있게 두는 것은 두 서비스와 다르다. 둘은 접수와 동시에 취소를 막는다.
본 서비스는 결제가 선불이고 행사장에서 급히 누르는 주문이 많아 되돌릴 여지를 둔다. 근거는 02 문서 2.10에 적었다.

화면 두 건(주문 접수, 주문 거절)과 Flow 한 건(미수령 주문 마감)이 늘었다.
근거는 `research/주문흐름_대조.md`에 있다. IS-043~IS-046은 해결로 닫았다.

### R-4 고객 화면에 넣어야 할 법정 항목을 확인했다

메뉴 표시 의무(원산지·알레르기·영양성분) 밖에 빠진 것이 있는지 확인했다. 세 가지가 빠져 있었다.

| 항목 | 근거 | 처분 | 반영 |
| --- | --- | --- | --- |
| 판매자 신원정보 | 전자상거래법 제13조 제1항 | 시정조치, 과태료 | 판매자 정보 화면을 웹앱과 키오스크에 둔다. 상권 등록에 통신판매업 신고번호를 받는다 |
| 개인정보 동의 고지 | 개인정보 보호법 제15조 제2항, 제22조 제1항 | 1천만원 이하 과태료 | 목적, 항목, 보유 기간, 거부권을 함께 보인다. 체크박스만 두지 않는다 |
| 취소 가능 구간 사전 고지 | 전자상거래법 제17조 제3항 | 청약철회 제한이 인정되지 않는다 | 결제 버튼 위에 취소 가능 구간을 적는다 |

판매자는 매장이다. 본사는 주문을 잇는 역할만 하므로 판매자로 표시하지 않는다.
값은 대부분 상권 등록의 본사 정보에 이미 있고 통신판매업 신고번호만 새로 받는다.

개인정보는 이름과 휴대폰번호 둘뿐이고 모두 주문 처리에 필요한 필수 항목이다.
선택 항목과 마케팅 동의는 두지 않는다. 두면 별도로 받아야 하고 거부해도 주문할 수 있어야 한다.

결제 상세 화면이 전자상거래법 제14조 제2항의 청약 확인 절차에 해당한다는 것을 05 문서에 적었다.
신용카드 매출전표는 결제대행사와 카드 단말이 발급하므로 본 서비스가 만들지 않는다.
주문 완료 화면의 주문서는 영수증이 아니다. 문서에서 '영수증'이라는 말을 쓰지 않는다.

근거는 `research/화면표시항목_조사.md`에 있다.

### R-5 서비스를 열기 전에 갖출 정책을 정리했다

법으로 갖춰야 하는 것 네 가지를 확인했다. 셋은 아직 문구가 없다.

| 항목 | 근거 | 상태 |
| --- | --- | --- |
| 개인정보 처리방침 | 개인정보 보호법 제30조 | 담을 항목만 정했다 (IS-047) |
| 이용약관 | 전자상거래법 제13조 제2항 | 거래조건 항목만 정했다 (IS-048) |
| 통신판매업 신고 | 전자상거래법 제12조 | 신고번호를 상권 등록에서 받는다 |
| 위치기반서비스사업 신고 | 위치정보법 제9조 | 신고 대상으로 보고 갖춘다 (IS-049) |

**위치기반서비스사업은 신고 대상으로 보고 갖춘다.** 면제 여부를 다투지 않는다.
판단이 갈리는 상태로 열면 동의 없이 위치정보를 수집·이용한 것이 되어
5년 이하 징역 또는 5천만원 이하 벌금까지 갈 수 있다. 갖추는 비용이 그 위험보다 작다.

동시에 **반경 판정은 단말에서 한다.** 신고를 하더라도 좌표를 서버로 보낼 이유가 없다.
보관하는 위치정보가 없으면 유출 위험도 없고 이용·제공 사실 확인자료도 남지 않는다.
위치 권한을 요청하기 전에 위치정보 이용 동의를 개인정보 동의와 따로 받는다.
선택 동의이므로 거부해도 주문할 수 있게 두고 반경 확인만 건너뛴다.

이용약관과 개인정보 처리방침을 볼 수 있는 경로를 판매자 정보 화면에 두었다.
이 둘은 아이오더가 정하고 전 매장에 같게 적용한다. 판매자 신원정보는 매장마다 다르다.

근거는 `research/필수정책_조사.md`에 있다.

### R-6 요구사항 문장을 표준 기준으로 점검했다

ISO/IEC/IEEE 29148 5.2.4와 5.2.7을 기준으로 요구사항, 화면 정책, 기능 명세의 조건과 예외를
자동으로 대조했다. `python tools/check_wording.py`로 다시 확인할 수 있다.

점검한 문장 650개에서 지적 0건이다. 최상급, 주관적 표현, 모호한 지시어, 개방형 표현,
빠져나갈 구멍, 전체성 함의, 권장 표현을 쓴 곳이 없다.

### R-7 상권을 여러 행사에 붙이면서 드러난 것

상권이 행사 여러 개에 참여할 수 있게 하면서 관계를 다시 봤다. 두 가지가 걸렸다.

**주문의 행사 귀속이 정해지지 않는다.** 상권이 세 행사에 참여하면 그 상권의 주문이
어느 행사 매출인지 상권만으로는 알 수 없다. 매장이 행사 하나에 속하도록 하고
매장을 등록할 때 상권의 참여 행사 중에서 고르기로 정했다.
행사 : 상권은 N:M, 행사 : 매장은 1:N이다. 이러면 주문 → 매장 → 행사가 하나로 정해진다 (IS-053).

**매장을 등록하는 화면이 없다.** FN-104 매장 등록에 대응하는 화면이 사라졌다.
확인해 보니 세 문서가 서로 어긋나 있었다.

| 문서 | 적혀 있던 것 |
| --- | --- |
| 01 REQ-004 | 본사 운영자가 상권에 매장을 등록한다 |
| 05 4.1 머리말 | 매장 등록은 가맹 어드민에서 한다 |
| 05 4.2 화면 목록 | 매장 등록 화면이 없다 |

REQ-004와 FN-104의 주체를 가맹 관리자로 맞추고, 가맹 어드민 설정 > 매장에 매장 목록과 매장 등록·수정 화면을 두었다.
등록할 때 상권의 참여 행사 중에서 소속 행사를 고른다. 폐점은 되돌릴 수 없고 연결 단말은 사용 중지로 바뀐다 (IS-052, IS-053 해결).

### R-9 매장 개설 절차를 정했다

누가 매장을 만들고 누가 여는지가 02, 03, 05 문서에서 서로 달랐다. 배달앱 입점, 프랜차이즈 개설, 축제 부스 선정 사례를 대조해 정했다. 근거는 `research/매장개설_조사.md`에 있다.

| 항목 | 결정 |
| --- | --- |
| 등록 | 가맹 관리자가 설정 > 매장에서 만든다. 저장하면 개설 준비다 |
| 확정 | 본사가 결제대행사 하위가맹점 심사 결과로 개시를 확정한다. 결과가 자동으로 오면 사람이 누르지 않는다 |
| 확정 전 | 주문 채널에 나오지 않고 정산에 들어가지 않는다. 소속 행사를 바꿀 수 있다. 메뉴와 단말은 미리 갖춘다 |
| 확정 후 | 영업이 되고 소속 행사가 잠긴다 |

본사 화면은 대시보드 개시 준비의 심사 열에서 여는 개시 확정 팝업 하나만 늘렸다. 확정 근거가 결제대행사 심사라 본사의 자의가 끼지 않고, 확정 전에는 정산에 들어가지 않아 매출 귀속 다툼이 없다.

### R-10 문서 사이 정합을 다시 맞췄다

화면, 요구사항, 기능, 추적표를 서로 대조해 어긋난 곳을 고쳤다.

| 지적 | 조치 |

화면 93건, Wireframe 202건, 기능 명세 93건이 서로 같은 이름과 유형, 상태값을 쓴다. 요구사항 47건과 기능 64건이 추적표와 일치한다.

| 주문 상세 (신설) | 결제와 승인번호, 상태 변경 이력, 알림 발송 결과를 한 팝업에. 본사는 조회만 하고 고치려면 대행 접속 |
| 내려받기 (신설) | 매출·정산·이력 화면 공통 팝업. 범위와 형식, 개인정보 포함 여부, 진행 막대와 완료 토스트, 실패 시 오류 번호 |

화면에 남아 있던 문서체 설명문 여덟 줄을 지웠다. 판매자 정보의 중개자 고지는 법으로 표시해야 하므로 말투만 고쳤다.
상권 화면에서는 참여 행사를 다루지 않는다. 붙이고 떼는 일은 행사 등록·수정의 상권 탭에서만 한다.

### R-14 매출을 행사·매장·메뉴 축으로 볼 수 있게 했다

매출 조회의 기준을 일자별에서 네 가지로 늘리고, 무엇이 팔렸는지 보는 화면을 새로 뒀다.

| 축 | 어디서 보는가 |
| --- | --- |
| 행사별 | 매출 조회의 기준을 행사별로 둔다. 매장 수와 기간을 함께 본다 |
| 상권별 | 행사별에서 행을 선택하면 그 행사의 상권별로 내려간다 |
| 매장별 | 상권별에서 내려가거나 기준을 매장별로 둔다. 객단가를 함께 본다 |
| 일자별 | 기본 기준이다. 매장별에서 행을 선택하면 그 매장의 하루치로 내려간다 |
| 카테고리별 | 메뉴 매출의 기준을 카테고리별로 둔다 |
| 메뉴별 | 카테고리 행을 선택하거나 기준을 메뉴별로 둔다 |

집계에서 갈릴 수 있는 세 가지를 못 박았다.

| 항목 | 정한 것 |
| --- | --- |
| 옵션 추가금 | 그 옵션을 붙인 메뉴에 넣는다. 옵션을 따로 세지 않는다 |
| 판매 수량 | 메뉴 수량의 합이다. 옵션은 수량으로 세지 않는다 |
| 카테고리 이름 | 카테고리는 브랜드에 속한다. 브랜드가 다르면 이름이 같아도 합치지 않는다 |

매출 조회의 순매출과 메뉴 매출의 순판매액은 같은 기간에서 일치해야 한다. 이 조건을 명세에 적었다.

### R-15 배치를 어드민 표준에 맞췄다

조회 조건 영역과 표 툴바, 주요 동작 자리를 국내외 디자인 시스템 원문으로 확인하고 적용했다. 근거는 `research/어드민레이아웃표준_조사.md`에 있다.

| 항목 | 준거 | 적용 |
| --- | --- | --- |
| 한 줄 조건 수 | Ant Design 고급 검색 | 세 개까지. 시작일과 종료일은 한 조건으로 센다. 단말 목록의 네 조건 줄을 나눴다 |
| 조건 순서 | Ant Design 고급 검색 | 넓은 범위에서 좁은 범위 순으로 두고 표의 열 순서와 맞춘다 |
| 조회·초기화 자리 | Ant Design Pro QueryFilter | 조건 칸 오른쪽 끝. 초기화를 왼쪽, 조회를 오른쪽에 둔다 |
| 등록 버튼 | Atlassian 페이지 머리말 | 머리말 오른쪽. 조회 조건 줄에 두지 않는다 |
| 표 위 동작 수 | Carbon 데이터 테이블 | 다섯 개까지 |
| 배치 액션과 페이지네이션 | Carbon 데이터 테이블 | 처리 줄은 표 바로 위, 페이지네이션은 표 아래 |
| 간격 | KRDS 8포인트 그리드 | 칸 12px, 줄 16px, 화면 안쪽 24px |

초기화를 조회 왼쪽으로 옮긴 이유는 잘못 누르는 위험 때문이다. 초기화는 입력한 조건을 지우고 되돌릴 수 없다.
주 동작 오른쪽에 두면 조회를 누르려다 초기화를 누르기 쉽다. 순서를 바꾸고 강조를 나눠 위험을 줄였다.

버튼 22줄의 순서를 바꾸고, 뷰어의 칸·줄 간격을 상황판 그리기 값과 같은 12px, 16px로 맞췄다.

표시 개수와 열 고르기, 조회 건수는 따로 줄을 만들지 않고 조회 버튼 오른쪽에 이어 두었다. 조회 버튼과의 사이에 여백을 넣어 오른쪽 끝에 붙인다. 빈 칸만 있는 줄이 남지 않는다.
