# 03. 서비스 구조

## 1. 서비스 구성

| 구성 | 대상 | 구축 순서 |
| --- | --- | --- |
| 내부 어드민 | 본사 운영자 | 1 |
| 가맹 어드민 | 가맹 관리자 | 2 |
| 하이브리드 웹앱 | 고객 | 3 |
| 키오스크 | 고객 | 4 |
| 외부 연계 | 외부 POS | 3단계와 병행 |

ERP가 행사, 상권, 매장, 카테고리, 메뉴 정보의 기준이다. 주문 채널과 외부 POS는 이 정보를 받아 쓴다.

## 2. 정보 계층

### 마스터 정보

```ia
본사 :: 전체 기준. 마스터 정보를 보유한다
  행사 :: 기간 단위 운영. 시작일·종료일
    상권 :: 지역 구분. 통계 비교 축
      매장 :: 브랜드, 지점번호, 영업시간, 채널 사용 여부
        *매장별 메뉴 설정 :: 판매가, 노출 여부, 품절 상태
  브랜드 :: 메뉴를 소유하는 단위
    카테고리 :: 상품 분류. 정렬 순서
      메뉴 :: 가격, 이미지, 판매 시간, 원산지, 알레르기
        옵션 그룹 :: 필수 여부, 최소·최대 선택 수
          옵션 항목 :: 추가금
```

점선 상자는 두 계열을 잇는 연결 객체다. 매장별 메뉴 설정은 매장과 메뉴를 함께 참조한다.

상권 하나에 브랜드 하나를 둔다. 상권명이 곧 브랜드명이다. 매장은 그 브랜드에 속하고 그 안에서 지점번호를 갖는다. 표시명은 브랜드명과 지점번호를 조합한다. 직영과 가맹은 구분하지 않는다.

### 거래 정보

```ia
주문 :: 매장, 채널, 주문 상태, 호출 순번, 주문자 이름·휴대폰번호
  주문 항목 :: 메뉴, 옵션, 수량, 단가
  결제 :: 결제 수단, 승인번호, 취소 이력
```

주문은 매장을 참조한다. 매장이 상권 하나와 행사 하나에 속하므로 매출을 행사와 상권 축으로 집계할 수 있다.
상권은 행사 여러 개에 참여할 수 있지만 매장은 행사 하나에 속한다. 그래서 주문이 어느 행사의 매출인지 하나로 정해진다.

### Level 정의

| Level | 객체 | 정의 | 관리 기능 |
| --- | --- | --- | --- |
| L1 | 본사 | 전체 기준. 마스터 정보의 소유자 | 계정·권한 관리 |
| L2 | 행사 | 기간 단위 운영 묶음 | 행사 관리 |
| L2 | 브랜드 | 메뉴를 소유하는 단위 | 브랜드 관리 |
| L3 | 상권 | 브랜드 하나에 대응하는 운영 묶음. 통계 비교 축. 행사 여러 개에 참여할 수 있다 | 상권 관리 |
| L3 | 카테고리 | 상품 분류. 집계와 관리에 사용 | 카테고리 관리 |
| L4 | 매장 | 실제 판매 장소. 상권과 행사 하나씩에 속하고 지점번호를 갖는다 | 매장 등록, 매장 상태 관리 |
| L4 | 메뉴 | 판매 단위. 원산지와 알레르기를 속성으로 가진다 | 메뉴 등록, 알레르기 등록 |
| L5 | 매장별 메뉴 설정 | 매장과 메뉴를 잇는 연결 객체 | 매장별 가격 설정, 품절 관리 |
| L5 | 옵션 그룹 | 메뉴에 연결하는 선택 묶음 | 옵션 관리 |
| L6 | 옵션 항목 | 개별 선택지 | 옵션 관리 |

### 객체 간 관계

| 상위 | 하위 | 관계 | 설명 |
| --- | --- | --- | --- |
| 본사 | 행사 | 1:N | 본사가 여러 행사를 운영한다 |
| 행사 | 상권 | N:M | 행사 하나에 상권 여러 개가 참여하고, 상권 하나가 행사 여러 개에 참여한다 |
| 상권 | 매장 | 1:N | 상권 하나에 매장 여러 개가 속한다 |
| 행사 | 매장 | 1:N | 매장은 행사 하나에 속한다. 상권의 참여 행사 중 하나를 고른다 |
| 본사 | 브랜드 | 1:N | 본사가 여러 브랜드를 운영한다 |
| 브랜드 | 매장 | 1:N | 매장은 브랜드 하나에 속한다 |
| 브랜드 | 카테고리 | 1:N | 카테고리는 브랜드가 소유한다 |
| 카테고리 | 메뉴 | 1:N | 메뉴는 카테고리 하나에 속한다 |
| 메뉴 | 옵션 그룹 | N:M | 옵션 그룹을 여러 메뉴에 연결한다 |
| 옵션 그룹 | 옵션 항목 | 1:N | 옵션 그룹 하나에 선택지 여러 개가 속한다 |
| 매장 | 메뉴 | N:M | 매장별 메뉴 설정으로 연결한다 |
| 매장 | 주문 | 1:N | 주문은 매장에서 발생한다 |
| 주문 | 주문 항목 | 1:N | 주문 하나에 항목 여러 개가 속한다 |
| 주문 항목 | 메뉴 | N:1 | 주문 시점의 메뉴와 단가를 보관한다 |
| 주문 | 결제 | 1:N | 취소와 재결제로 결제가 여러 건 생길 수 있다 |

### 구조 판단

**메뉴는 브랜드가 소유한다.** 카테고리와 메뉴를 매장 아래에 두면 매장 수만큼 같은 메뉴가 중복된다. 같은 브랜드의 매장은 같은 메뉴를 쓰므로 브랜드가 소유하고 매장이 참조한다.

**매장과 메뉴는 연결 객체로 잇는다.** 판매가, 노출 여부, 품절 상태는 매장마다 다르다. 메뉴에 직접 두면 매장별 값을 담을 수 없고, 매장에 두면 메뉴 정보가 중복된다.

**직영과 가맹을 구분하지 않는다.** 두 유형 사이에 메뉴, 가격, 권한의 정책 차이가 없다. 지점번호는 브랜드 안에서의 일련번호이며 계층이 아니다.

**옵션은 메뉴의 하위 계층이 아니다.** 같은 옵션 그룹을 여러 메뉴에 연결한다. 온도 선택처럼 공통으로 쓰는 묶음이 여기에 해당한다.

**알레르기와 원산지는 메뉴의 속성이다.** 별도 계층으로 두지 않는다. 옵션 선택에 따라 알레르기 유발물질이 달라지면 메뉴를 복제해 각각 등록한다.

**관리축과 표시축을 분리한다.** 카테고리는 집계와 관리에 쓴다. 채널별 노출 순서와 배치는 별도로 관리한다. 같은 구조로 다루면 메뉴를 다시 저장할 때 채널 설정이 덮어써진다.

## 3. 코드 체계

조사 근거는 `research/코드체계_조사.md`에 있다. 표준이 있는 항목은 참조하고, 없는 항목만 자체 정의한다.

### 참조하는 공개 표준

| 항목 | 표준 | 형식 | 저장 방식 |
| --- | --- | --- | --- |
| 매장 주소의 행정구역 | 행정표준코드 행정동코드 | 숫자 10자리. 실무는 앞 8자리 사용 | 문자열. 선행 0을 유지한다 |
| 매장 주소의 법정 구역 | 행정표준코드 법정동코드 | 숫자 10자리 | 문자열 |
| 매장 사업자 | 사업자등록번호 | 10자리 | 문자열. 검증번호로 형식을 확인한다 |
| 매장 지점 | 종사업장번호 | 4자리 | 문자열 |
| 매장 업종 | 한국표준산업분류 제11차 | 음식점업은 대분류 I, 중분류 56 | 문자열 |
| 알레르기 유발물질 | 어린이 기호식품 등의 알레르기 유발 식품 표시기준 및 방법 | 18종. 명칭만 있고 코드가 없다 | 명칭을 고시 원문과 글자 단위로 일치시킨다. 별표 2의 19종은 가공식품 기준이므로 쓰지 않는다 |
| 영양성분 | 어린이식생활안전관리특별법 고시 별표 1 | 음식점 의무 표시 5종 | 성분별 수치와 기준량을 함께 보관한다. 9종은 가공식품 기준이다 |
| 원산지 표시 대상 | 원산지표시법 시행령 제3조 제5항 | 30품목. 명칭만 있고 코드가 없다 | 명칭을 법령 원문과 일치시킨다 |
| 원산지 국가 | 국가표준코드 | 2자리 영문 | 문자열. 표시 문구는 한글 국가명을 쓴다 |

전국 단위 상권 코드는 공개된 것이 없다. 서울시 상권코드는 서울에 한정되고 상업적 이용이 가능하나 전국을 덮지 못한다. 따라서 상권은 자체 코드로 관리하고 행정동코드를 참조 항목으로 함께 보관한다. 외부 상권 데이터와 결합할 때 연결 고리가 된다.

### 자체 정의하는 코드

| 대상 | 형식 | 예 |
| --- | --- | --- |
| 행사 | EV + 연도 4자리 + 일련 3자리 | EV2026001 |
| 브랜드 | BR + 일련 4자리 | BR0001 |
| 상권 | ZN + 일련 5자리 | ZN00001 |
| 매장 | ST + 일련 6자리 | ST000001 |
| 지점번호 | 브랜드 안의 일련번호. 코드가 아니라 정수 속성 | 1, 2, 3 |
| 카테고리 | CT + 일련 5자리 | CT00001 |
| 메뉴 | MN + 일련 7자리 | MN0000001 |
| 옵션 그룹 | OG + 일련 5자리 | OG00001 |
| 옵션 항목 | OI + 일련 6자리 | OI000001 |
| 주문 | OD + 영업일 8자리 + 일련 6자리 | OD20260904000001 |
| 결제 | PY + 영업일 8자리 + 일련 6자리 | PY20260904000001 |
| 알레르기 유발물질 | AL + 순번 2자리 | AL01 |
| 원산지 표시 품목 | OR + 순번 2자리 | OR01 |

### 코드 설계 규칙

* 코드는 문자열로 저장한다. 선행 0이 의미를 갖고, 외부 코드는 자리수가 문서마다 다른 경우가 있다.
* 상위 코드를 하위 코드의 접두사로 넣지 않는다. 매장이 다른 상권으로 옮겨질 때 코드를 바꾸지 않기 위해서다. 계층은 참조 항목으로 표현한다.
* 한 번 부여한 코드는 바꾸지 않는다. 대상이 삭제되어도 재사용하지 않는다.
* 코드값과 의미를 하나로 유지한다. 의미가 바뀌면 새 값을 부여한다.
* 외부 코드는 원본 그대로 보관한다. 우리 형식으로 바꾸지 않는다.
* 컬럼명과 데이터 형식은 공통표준용어와 공통표준도메인을 준용한다.

### 법령 명칭을 코드로 다룰 때의 주의

알레르기 유발물질과 원산지 표시 품목은 법령이 명칭만 규정한다. 내부 코드는 조회와 정렬을 위해 부여하되, 화면과 출력물에는 법령 원문의 명칭을 그대로 쓴다. 명칭이 다르면 표시 위반이 된다.

알레르기 유발물질은 참깨, 들깨, 아몬드, 캐슈너트 4종 추가가 입법예고되어 있다. 확정되면 23종이 된다. 목록을 코드 테이블로 관리해 추가에 대응한다.

## 4. 사용자 유형

| ID | 사용자 유형 | 정의 | 접근 범위 |
| --- | --- | --- | --- |
| UT-01 | 본사 운영자 | 행사와 브랜드를 등록하고 가맹 어드민 계정을 발급한다. 전체 매출과 정산을 확인한다. 매장 운영에는 관여하지 않는다 | 전체 |
| UT-02 | 가맹 관리자 | 담당 매점의 운영 정보를 관리한다 | 담당 매장 |
| UT-03 | 고객 | 하이브리드 웹앱 또는 키오스크로 주문한다. 회원 가입 없이 비회원으로 주문한다 | 주문 채널 |

역할 부여와 데이터 범위 제한은 분리해 관리한다. 역할이 있다는 것과 특정 매장만 보인다는 것은 별개의 통제다. 매장이 늘어날 때마다 권한 정의를 고치지 않도록 데이터 범위는 조직 계층 기준으로 판정한다.

## 6. 서비스 아키텍처

### 6.1 시스템 구성

```arch
== 운영 주체 ==
[본사]
담당: 본사 운영자
[매장]
담당: 가맹 관리자
[고객]
이용: 웹앱 이용자, 키오스크 이용자
== 채널 ==
[운영 화면]
어드민: 내부 어드민, 가맹 어드민
[주문 화면]
자사: 하이브리드 웹앱, 키오스크
== 업무 도메인 ==
[기준정보]
관리: 행사, 상권, 브랜드, 매장
[상품]
관리: 카테고리, 메뉴, 옵션, 표시 정보, 매장별 가격, 품절
[주문]
관리: 주문 생성, 상태 전이, 접수, 취소
[결제]
관리: 승인, 취소, 결제 원장, 대사
[매출]
관리: 집계, 행사와 상권 비교
== 외부 ==
[결제 연계]
외부: 결제대행사, 카드 단말
[알림 연계]
외부: 알림톡
[채널 연계]
외부: 외부 POS
@ 본사 -> 운영 화면 : 기준정보와 상품 관리
@ 매장 -> 운영 화면 : 매장 운영과 주문 접수
@ 고객 -> 주문 화면 : 주문 요청
@ 운영 화면 -> 기준정보 : 등록과 수정
@ 운영 화면 -> 상품 : 등록과 수정
@ 주문 화면 -> 주문 : 주문 생성 요청
@ 기준정보 => 상품 : 소속 관계 참조
@ 상품 -> 주문 화면 : 메뉴와 가격
@ 상품 -> 채널 연계 : 변경 통지
@ 주문 -> 결제 : 승인과 취소 요청
@ 결제 -> 결제 연계 : 승인 요청
@ 결제 -> 주문 : 승인 결과
@ 주문 => 매출 : 집계 원본
@ 결제 => 매출 : 집계 원본
@ 매출 -> 운영 화면 : 조회 결과
@ 주문 -> 알림 연계 : 상태 알림
!도메인은 여섯 개로 묶었다. 품절, 카테고리, 행사를 각각 독립 시스템으로 두지 않는다. 변경 주기와 관리 주체가 같으면 한 도메인 안에 둔다.
!점선은 데이터 참조와 동기화다. 실선은 업무 요청과 결과 전달이다.
!배포 도메인을 두지 않는다. 매장이 원본을 가지므로 내려보낼 것이 없다.
!결제를 주문에서 분리한 근거는 셋이다. 외부 응답에 좌우되고, 실패 경로가 주문과 다르며, 보관 기간과 접근 통제 기준이 다르다.
!매출은 파생 도메인이다. 주문과 결제를 원본으로 삼고 자체 원본을 갖지 않는다.
!외부 POS는 채널이 아니라 외부 시스템이다. 우리가 만들지 않으며 화면과 주문 처리를 통제하지 않는다.
```

### 6.2 내부 어드민

본사 운영자가 쓴다. 기준정보를 만들고, 가맹 관리자 계정을 발급하고, 전체 매장의 결제 실적을 본다.

메뉴는 만들지 않는다. 매장이 등록한다. 내려보낼 것이 없으므로 배포 화면도 두지 않는다.

가맹 관리자 계정은 여기서만 만든다. 가맹 어드민에 회원가입이 없다. 계정을 만들 때 담당 매장 범위를 함께 지정한다.

```arch
== 이용자 ==
[본사 운영자]
권한: 전체 매장
== 화면 ==
[기준정보 화면]
메뉴: 대시보드, 행사, 상권, 매출, 정산, 시스템
[매출 화면]
메뉴: 매출 조회, 행사와 상권 비교
[시스템 화면]
메뉴: 계정 관리, 접속기록, 단말 상태, 연동 계정
== 도메인 ==
[기준정보]
원본: 행사, 상권, 브랜드, 매장
[매출]
파생: 집계 테이블
[인증과 권한]
원본: 계정, 역할, 담당 매장 범위
@ 본사 운영자 -> 기준정보 화면 : 등록과 수정
@ 본사 운영자 -> 매출 화면 : 실적 조회
@ 본사 운영자 -> 시스템 화면 : 계정 발급과 점검
@ 기준정보 화면 -> 기준정보 : 저장
@ 매출 화면 => 매출 : 조회
@ 시스템 화면 -> 인증과 권한 : 계정과 범위 지정
!본사는 메뉴를 만들지 않는다. 배포 화면을 두지 않는다.
!가맹 관리자 계정은 본사가 발급한다. 가맹 어드민에 회원가입 절차를 두지 않는다.
!매출 화면은 원본을 직접 읽지 않는다. 집계 테이블을 읽는다.
```

### 6.3 가맹 어드민

가맹 관리자가 쓴다. 담당 매장의 메뉴를 만들고 주문을 받는다.

메뉴, 카테고리, 옵션, 판매가, 표시 정보, 품절이 모두 여기에 있다. 저장하면 그 매장의 주문 채널에 반영된다. 발행 절차가 없다.

표시 정보를 입력하지 않은 메뉴는 판매 불가 상태로 남는다. 누락이 운영으로 넘어가지 않게 막는다.

```arch
== 이용자 ==
[가맹 관리자]
권한: 담당 매장
== 화면 ==
[매점 홈]
메뉴: 접수 대기 현황, 단말기 설정
[메뉴 관리 화면]
메뉴: 메뉴 목록, 등록과 수정, 표시 정보
분류: 카테고리, 옵션 그룹, 판매가, 품절
[주문 화면]
메뉴: 주문 접수, 주문 상세, 주문서 출력
[매점 정보 화면]
메뉴: 정보 조회, 정보 변경, 영업 상태
[매출 화면]
메뉴: 담당 매장 매출
== 도메인 ==
[상품]
원본: 카테고리, 메뉴, 옵션, 표시 정보, 판매가, 품절
[주문]
원본: 주문, 주문 상태
[기준정보]
조회: 매장 정보
[매출]
파생: 담당 매장 집계
@ 가맹 관리자 -> 매점 홈 : 현황 확인
@ 가맹 관리자 -> 메뉴 관리 화면 : 등록과 수정
@ 가맹 관리자 -> 주문 화면 : 접수와 상태 변경
@ 가맹 관리자 -> 매점 정보 화면 : 정보 변경
@ 가맹 관리자 -> 매출 화면 : 실적 조회
@ 메뉴 관리 화면 -> 상품 : 저장
@ 주문 화면 -> 주문 : 상태 전이
@ 매점 정보 화면 => 기준정보 : 정보 변경과 이력 기록
@ 매출 화면 => 매출 : 담당 범위 조회
!메뉴의 원본은 매장이다. 본사가 만들지 않는다.
!저장과 반영을 분리하지 않는다. 저장하면 주문 채널에 반영된다.
!표시 정보 미입력 메뉴는 판매 불가 상태로 둔다.
!매점 정보는 매장이 바로 바꾼다. 본사 확정을 두지 않고 변경 이력만 남긴다.
!조회 범위는 담당 매장으로 제한한다.
```

### 6.4 하이브리드 웹앱

고객이 쓴다. 회원 가입이 없다. 주문번호와 휴대폰번호로 주문을 조회한다.

매장 선택 화면을 두지 않는다. QR에 담긴 매장으로 바로 들어간다. 매장을 고르는 절차가 없으므로 잘못된 매장에 주문하는 일이 생기지 않는다.

앱스토어에 등록하지 않으므로 결제 앱에서 돌아올 때 상점 앱으로 복귀하는 경로가 없다. 결과를 리다이렉트로 확정하지 않는다.

```arch
== 이용자 ==
[고객]
접근: QR, 링크
== 화면 ==
[진입 화면]
메뉴: QR 진입, 수령 방식
[주문 화면]
메뉴: 메뉴 목록, 메뉴 상세, 장바구니
[결제 화면]
메뉴: 주문서, 결제 진행, 주문 완료
[조회 화면]
메뉴: 주문 조회, 주문 상태, 주문 취소
== 도메인 ==
[상품]
조회: 매장 메뉴와 가격
[주문]
원본: 주문, 주문 상태
[결제]
원본: 승인, 취소, 결제 원장
== 외부 ==
[결제대행사]
처리: 인증, 승인, 취소
[알림톡]
처리: 상태 통지
@ 고객 -> 진입 화면 : QR 스캔
@ 고객 -> 주문 화면 : 메뉴 선택
@ 고객 -> 결제 화면 : 주문서 작성과 결제
@ 고객 -> 조회 화면 : 주문번호와 휴대폰번호
@ 상품 => 주문 화면 : 메뉴와 가격
@ 결제 화면 -> 주문 : 주문 생성 요청
@ 주문 -> 결제 : 승인 요청
@ 결제 -> 결제대행사 : 승인과 취소
@ 결제대행사 => 결제 : 승인 결과 웹훅
@ 주문 -> 알림톡 : 접수와 완료 통지
!결제 결과를 리다이렉트로 확정하지 않는다. 서버 승인과 웹훅, 조회를 함께 둔다.
!승인에 성공해야 주문을 만든다. 실패하면 주문이 남지 않는다.
!회원 개념이 없다. 주문번호와 휴대폰번호로만 조회한다.
!매장 선택 화면이 없다. QR에 매장이 담겨 있지 않으면 진입하지 않는다.
```

### 6.5 키오스크

매장에 설치한다. 고객이 주문하고 가맹 관리자가 관리자 모드로 들어온다.

카드 승인은 단말이 처리한다. 플랫폼은 결과만 받는다. 네트워크가 끊겨도 마지막으로 받은 메뉴로 화면을 유지한다.

```arch
== 이용자 ==
[고객]
행위: 현장 주문
[가맹 관리자]
행위: 관리자 모드
== 화면 ==
[주문 화면]
메뉴: 대기, 취식유형, 메뉴 선택, 장바구니
[결제 화면]
메뉴: 결제수단, 단말 승인, 완료
[관리자 화면]
메뉴: 메뉴 갱신, 판매 메뉴 설정, 품절 설정, 단말 상태
== 단말 ==
[키오스크 단말]
보관: 메뉴 마스터 사본
처리: 화면 표시, 주문표 출력
== 도메인 ==
[상품]
조회: 매장 메뉴
[주문]
원본: 주문, 주문번호
[결제]
원본: 승인 결과, 거래 기록
== 외부 ==
[카드 단말]
처리: 현장 승인, 망취소
@ 고객 -> 주문 화면 : 메뉴 선택
@ 고객 -> 결제 화면 : 결제 진행
@ 가맹 관리자 -> 관리자 화면 : 인증 후 진입
@ 상품 => 키오스크 단말 : 유휴와 결제 완료 시점에 수신
@ 키오스크 단말 -> 주문 화면 : 로컬 사본으로 표시
@ 결제 화면 -> 카드 단말 : 승인 요청
@ 카드 단말 -> 결제 : 승인 결과
@ 결제 -> 주문 : 주문 생성
@ 관리자 화면 -> 결제 : 거래 조회와 환불
!카드 승인은 단말과 카드사 사이에서 처리한다. 플랫폼은 결과만 받는다.
!네트워크가 끊기면 마지막으로 받은 메뉴로 화면을 유지한다. 주문 접수는 복구 후 처리한다.
!메뉴 마스터는 주문 중에 바뀌지 않는다. 유휴 시점과 결제 완료 시점에만 받는다.
```

### 6.6 결제와 정산

주문에서 분리한 영역이다. 외부 응답에 좌우되고 실패 경로가 주문과 다르다.

플랫폼은 대금을 수취하지 않는다. 결제대행사가 매장에 직접 정산하고 우리는 대사만 한다.

```arch
== 요청 ==
[주문]
요청: 승인, 취소
== 처리 ==
[결제]
관리: 금액 검증, 승인, 취소, 결제 원장
대사: 거래대사, 정산대사, 입금대사
== 외부 ==
[결제대행사]
처리: 승인 중계, 매장 정산
[카드 단말]
처리: 현장 승인
[카드사]
처리: 매입, 대금 지급
@ 주문 -> 결제 : 승인과 취소 요청
@ 결제 -> 결제대행사 : 승인 요청. 웹앱
@ 결제 -> 카드 단말 : 승인 요청. 키오스크
@ 결제대행사 -> 카드사 : 매입 요청
@ 카드사 -> 결제대행사 : 대금 입금
@ 결제대행사 => 결제 : 승인 결과와 정산 내역
@ 결제 -> 주문 : 승인과 취소 결과
!플랫폼은 자금 경로에 없다. 결제대행사가 매장에 직접 정산한다.
!정산 내역은 대사에만 쓴다. 매장별 정산금액을 계산하지 않는다.
!대사는 거래, 정산, 입금 세 단계로 나눈다. 조회 기준일과 취소 상계 여부를 단계마다 정한다.
```

### 6.7 시스템별 책임

| 도메인 | 존재 이유 | 관리 데이터 | 주요 연계 |
| --- | --- | --- | --- |
| 기준정보 | 다른 모든 도메인이 참조하는 조직과 장소를 한 곳에서 정한다 | 행사, 상권, 브랜드, 매장, 소속 관계 | 상품, 주문, 매출, 외부 POS |
| 상품 | 매장이 무엇을 얼마에 파는지 정한다 | 카테고리, 메뉴, 옵션, 알레르기와 원산지, 판매가, 품절 상태 | 주문, 외부 POS |
| 주문 | 주문의 생성과 상태를 관리한다 | 주문, 주문 항목, 주문 상태, 취소 사유 | 결제, 매출, 매장 화면 |
| 결제 | 승인과 취소를 처리하고 거래 기록을 보관한다 | 결제 원장, 승인번호, 매입 상태, 취소 이력, 대사 결과 | 주문, 매출, 결제 연계 |
| 매출 | 주문과 결제를 집계해 비교 가능한 형태로 만든다 | 집계 테이블, 잠정과 확정 구분 | 운영 화면 |
| 인증과 권한 | 누가 무엇에 접근하는지 판정한다 | 계정, 역할, 담당 범위 | 모든 도메인 |
| 기록 | 누가 무엇을 했는지 남긴다 | 접속기록, 작업 이력, 단말 상태 | 운영 화면 |
| 전달 | 외부로 나가는 알림과 파일을 처리한다 | 발송 이력, 이미지 | 알림 연계 |

### 6.8 기준 데이터

각 데이터의 원본이 되는 도메인을 정한다. 원본이 아닌 곳에서는 복사본을 참조만 한다.

| 데이터 | 기준 도메인 | 참조하는 곳 |
| --- | --- | --- |
| 행사, 상권, 브랜드, 매장 | 기준정보 | 상품, 주문, 매출, 외부 POS |
| 카테고리, 메뉴, 옵션, 표시 정보 | 상품 | 주문, 외부 POS |
| 판매가 | 상품 | 주문, 외부 POS |
| 품절 상태 | 상품 | 주문, 외부 POS |
| 주문과 주문 상태 | 주문 | 매장 화면, 매출 |
| 결제 승인, 취소, 매입 상태 | 결제 | 주문, 매출 |
| 정산 내역 | 외부 결제대행사 | 결제. 대사에만 쓴다 |
| 매출 집계 | 매출 | 운영 화면 |

두 가지를 명시한다.

정산 내역은 우리가 원본이 아니다. 결제대행사가 산출하고 우리는 대조만 한다. 플랫폼이 정산금액을 계산하면 전자지급결제대행업 등록 대상이 된다.

매출은 결제 승인 금액을 기준으로 집계한다. 주문 금액은 참조값이다. 부분취소가 있으면 두 값이 달라진다.

### 6.9 주요 흐름

#### 매장 개설

```text
[본사] 기준정보에 행사, 상권, 브랜드, 매장 등록
 ↓
[본사] 가맹 관리자 계정 발급
 ↓
[매장] 카테고리, 메뉴, 옵션, 표시 정보 등록
 ↓
표시 정보 입력 완료?
 ├─ 아니오 → 판매 불가 상태로 저장
 └─ 예 → 다음
 ↓
주문 화면과 외부 POS가 반영
```

#### 주문과 결제

```text
고객이 주문 화면에서 장바구니 확정
 ↓
주문이 금액을 서버에서 재계산
 ↓
금액 일치?
 ├─ 아니오 → 승인을 요청하지 않는다
 └─ 예 → 다음
 ↓
결제가 승인 요청
 ↓
승인 성공?
 ├─ 아니오 → 주문을 만들지 않는다
 └─ 예 → 다음
 ↓
주문 생성. 상태는 접수 대기
 ↓
매장 화면에 전달
 ↓
매장이 접수. 상태 전이
 ↓
수령 완료
 ↓
매출이 결제 원장을 읽어 집계
```

#### 취소

```text
고객 또는 매장이 취소 요청
 ↓
주문이 취소 가능 여부 판정
 ↓
조리 시작 전?
 ├─ 아니오 → 매장 문의로 안내
 └─ 예 → 다음
 ↓
결제가 취소 요청
 ↓
취소 성공?
 ├─ 아니오 → 주문 상태를 바꾸지 않는다
 └─ 예 → 주문 상태 = 취소
 ↓
매출이 취소 일자에 차감
```

주문을 만들기 전에 결제를 승인한다. 승인에 실패하면 주문이 남지 않는다. 취소는 반대로 결제 취소가 성공해야 주문 상태를 바꾼다. 두 쪽 모두 결제가 확정된 뒤에 주문이 움직인다.

### 6.10 연결의 성격

| 구간 | 성격 | 오가는 것 |
| --- | --- | --- |
| 기준정보 → 상품 | 데이터 참조 | 브랜드와 매장의 소속 관계 |
| 상품 → 주문 화면 | 데이터 제공 | 메뉴와 가격 |
| 상품 → 외부 POS | 이벤트 전달 | 변경 통지. 상대가 조회해 간다 |
| 주문 화면 → 주문 | 업무 요청 | 주문 생성 요청 |
| 주문 → 결제 | 업무 요청 | 승인 요청과 취소 요청 |
| 결제 → 결제 연계 | API 연계 | 승인, 취소, 대사 조회 |
| 결제 연계 → 결제 | 이벤트 전달 | 승인 결과 웹훅 |
| 결제 → 주문 | 상태 변경 | 승인과 취소 결과 |
| 주문 → 매장 화면 | 이벤트 전달 | 신규 주문 알림 |
| 주문, 결제 → 매출 | 데이터 동기화 | 집계 원본 |
| 전달 → 알림 연계 | API 연계 | 발송 요청 |

### 6.11 설계 결정이 필요한 사항

| 항목 | 결정할 것 | 정해지지 않으면 |
| --- | --- | --- |
| 접수 실패 시 취소 주체 | 매장이 접수하지 않아 자동 취소될 때 결제 취소를 주문이 요청하는가, 매장 화면이 요청하는가 | 취소 실패 시 책임 지점이 불분명해진다 |
| 매출 확정 기준 | 승인 완료를 기준으로 볼지 매입 완료를 기준으로 볼지 | 매입 지연 건의 매출 계상 시점이 달라진다 |
| 외부 POS의 역할 범위 | 조회 제공까지인지 주문 유입까지인지 | 주문 유입이 생기면 주문 도메인의 경계가 바뀐다 |

### 6.12 기술 구성

업무 도메인을 실행 단위와 저장소에 배치한 결과다.

```arch
== 접점 ==
[고객 채널]
자사: 하이브리드 웹앱, 키오스크
[운영 채널]
어드민: 내부 어드민, 가맹 어드민
[외부 채널]
연동: 외부 POS
== 처리 ==
[진입]
공통: 로드밸런서, 정적 자원 배포
[동기 실행]
서비스: 주문 API, 어드민 API
[비동기 실행]
작업: 집계 배치, 알림 워커
== 보관 ==
[운영 데이터]
원본: 기준정보, 상품, 주문, 결제
보조: 캐시, 이미지 저장소
[분석 데이터]
파생: 매출 집계 테이블
기록: 접속기록, 작업 이력, 단말 상태
== 외부 ==
[결제]
연동: 결제대행사, 카드 단말
[알림]
발송: 알림톡
@ 고객 채널 -> 진입 : 주문과 결제 요청
@ 운영 채널 -> 진입 : 관리 요청
@ 외부 채널 -> 진입 : 조회 요청
@ 진입 -> 동기 실행 : 인증과 권한 확인 후 전달
@ 동기 실행 -> 운영 데이터 : 읽기와 쓰기
@ 동기 실행 -> 비동기 실행 : 작업 등록
@ 비동기 실행 -> 운영 데이터 : 읽기
@ 비동기 실행 -> 분석 데이터 : 집계 결과 적재
@ 비동기 실행 -> 알림 : 발송 요청
@ 동기 실행 -> 결제 : 승인과 취소
@ 분석 데이터 => 동기 실행 : 조회 응답
!어드민 접속은 IP 제한과 안전한 인증수단을 적용한다. 계정과 비밀번호만으로는 요건을 충족하지 않는다.
!집계 배치는 주문 API와 다른 실행 단위로 배포한다. 같은 프로세스에 두면 대량 작업이 주문 처리 자원을 잠식한다.
!카드 단말 승인은 매장 키오스크와 단말 사이에서 처리한다. 플랫폼은 승인 결과만 받는다.
!개인정보는 서울 리전 밖으로 내보내지 않는다. 국외이전 절차를 피할 수 있다.
!메시지 큐는 키오스크 단계에서 도입한다. 그 전에는 커밋 후 발행과 실패 로그로 처리한다.
```

## 7. 시스템 연계 구조

### 본사 운영자

본사 운영자는 기준정보를 등록하고, 매장 계정을 발급하며, 전체 매출과 정산 대사를 확인한다.

```arch
== 이용자 ==
[본사 운영자]
업무: 기준정보 등록, 계정 발급, 매출 확인, 정산 대사
== 운영 화면 ==
[내부 어드민]
기준정보: 행사, 상권, 브랜드, 매장
운영: 계정 발급, 매출 통계, 정산 대사
[가맹 어드민]
발급 결과: 매장 계정
== 데이터 ==
[플랫폼 데이터]
원본: 기준정보, 주문, 결제
파생: 매출 집계
== 외부 시스템 ==
[결제대행사]
제공: 거래 내역, 정산 내역
@ 본사 운영자 -> 내부 어드민 : 등록과 조회
@ 내부 어드민 -> 가맹 어드민 : 계정 발급
@ 내부 어드민 -> 플랫폼 데이터 : 기준정보 저장
@ 플랫폼 데이터 => 내부 어드민 : 매출과 결제 내역
@ 결제대행사 => 내부 어드민 : 대사 대상 내역
!본사는 메뉴와 판매가를 직접 다루지 않는다. 상품 정보의 주체는 매장이다.
!정산 내역은 대사에만 쓴다. 플랫폼이 정산금액을 계산하지 않는다.
```

### 가맹 관리자

매장은 메뉴와 판매가를 등록하고 주문을 접수한다. 저장한 내용은 플랫폼 데이터를 거쳐 주문 채널과 외부 시스템에 반영된다.

```arch
== 이용자 ==
[가맹 관리자]
업무: 메뉴 등록, 주문 접수, 매출 확인
== 운영 화면 ==
[가맹 어드민]
상품: 카테고리, 메뉴, 옵션, 판매가
운영: 주문 접수, 품절, 매장 정보
== 데이터 ==
[플랫폼 데이터]
원본: 상품, 주문, 결제
파생: 매출 집계
== 반영 대상 ==
[하이브리드 웹앱]
반영: 메뉴, 가격, 품절
[키오스크]
반영: 메뉴, 가격, 품절
[외부 POS]
반영: 변경 통지 후 조회
[알림톡]
반영: 주문 상태 통지
@ 가맹 관리자 -> 가맹 어드민 : 등록과 접수
@ 가맹 어드민 -> 플랫폼 데이터 : 메뉴와 주문 상태 저장
@ 플랫폼 데이터 => 가맹 어드민 : 주문과 매출 조회
@ 플랫폼 데이터 -> 하이브리드 웹앱 : 메뉴와 가격
@ 플랫폼 데이터 -> 키오스크 : 메뉴와 가격
@ 플랫폼 데이터 -> 외부 POS : 변경 통지
@ 플랫폼 데이터 -> 알림톡 : 주문 상태 통지
!외부 POS는 우리가 만들지 않는다. 변경 통지로 매장 식별자와 변경 시각만 보내고 상대가 조회해 간다.
!키오스크는 유휴 시점과 결제 완료 시점에 메뉴를 확인한다. 주문 중에는 화면이 바뀌지 않는다.
```

### 고객

고객은 주문 채널에서 주문하고 결제한다. 결제 승인 경로는 채널에 따라 나뉜다.

```arch
== 이용자 ==
[고객]
업무: 메뉴 선택, 주문, 결제
== 주문 채널 ==
[하이브리드 웹앱]
처리: QR 진입, 비회원 주문, 결제대행사 결제
[키오스크]
처리: 현장 주문, 카드 단말 결제
== 데이터 ==
[플랫폼 데이터]
원본: 주문, 주문 항목, 결제
== 외부 시스템 ==
[결제대행사]
처리: 승인, 취소
[카드 단말]
처리: 현장 승인
[알림톡]
처리: 고객 통지
@ 고객 -> 하이브리드 웹앱 : QR 진입 후 주문
@ 고객 -> 키오스크 : 현장 주문
@ 하이브리드 웹앱 -> 플랫폼 데이터 : 주문 저장
@ 키오스크 -> 플랫폼 데이터 : 주문 저장
@ 플랫폼 데이터 -> 결제대행사 : 승인 요청
@ 플랫폼 데이터 -> 카드 단말 : 승인 요청
@ 결제대행사 => 플랫폼 데이터 : 승인 결과
@ 카드 단말 => 플랫폼 데이터 : 승인 결과
@ 플랫폼 데이터 -> 알림톡 : 주문 상태 통지
!웹앱은 결제대행사, 키오스크는 카드 단말을 쓴다. 두 경로의 결제 원장은 하나로 합친다.
!점선은 결과 수신이다. 실선은 요청과 통지다.
```

### 결제 데이터 관리

플랫폼 자체 결제 식별자를 최상위 키로 두고 채널별 식별자를 덧붙인다. 승인번호는 PG와 VAN 공통이다. 취소 시 원거래 참조 키는 채널마다 다르다.

매출은 채널을 통합해 집계한다. 정산은 통합하지 않는다. VAN 대금은 카드사가 가맹점에 직접 지급하고 플랫폼을 거치지 않는다.

## 8. 화면 분류 기준

화면을 사용자로 나누지 않는다. 그 화면이 다루는 업무 영역과 그 업무의 주체로 나눈다.

사용자로 나누면 같은 업무를 두 번 정의하게 된다. 본사와 매장이 같은 데이터를 보는 화면이 각각 생기고, 규칙이 갈라진다.

| 기준 | 내용 |
| --- | --- |
| 1차 분류 | 업무 영역으로 나눈다. 기준정보, 상품, 주문, 매출, 정산, 단말, 알림, 계정과 보안, 운영 아홉 개다 |
| 2차 분류 | 그 업무를 실행하는 주체가 있는 쪽에 화면을 둔다. 본사가 실행하면 내부 어드민, 매장이 실행하면 가맹 어드민이다 |
| 상대의 접근 | 반대쪽이 그 화면을 볼 필요가 있으면 화면을 새로 만들지 않는다. 같은 화면에 데이터 범위와 동작 권한을 다르게 준다 |
| 화면을 나누는 경우 | 같은 데이터를 보더라도 답하려는 질문이 다르면 화면을 나눈다 |
| 화면ID | 앞자리는 최초 정의 위치다. 소속이 바뀌어도 식별자는 바꾸지 않는다 |

업무 영역별 주체와 상대의 접근 범위는 다음과 같다.

| 업무 영역 | 실행 주체 | 화면 위치 | 상대의 접근 |
| --- | --- | --- | --- |
| 기준정보 | 본사 | 내부 어드민 | 매장은 자기 매장 정보를 조회하고 변경을 요청한다 |
| 상품 | 매장 | 가맹 어드민 | 본사는 관여하지 않는다. 시스템이 필수 항목 누락만 막는다 |
| 주문 | 매장 | 가맹 어드민 | 본사는 매장 상세의 주문 탭에서 조회한다 |
| 매출 | 본사와 매장 | 양쪽 | 질문이 달라 화면을 나눈다. 아래에 근거를 적는다 |
| 정산 | 본사 | 내부 어드민 | 매장은 접근하지 않는다 |
| 단말 | 매장 | 가맹 어드민 | 본사는 같은 화면을 전체 범위로 보고 장애 시 사용 중지한다 |
| 알림 | 매장 | 가맹 어드민 | 본사는 같은 화면을 전체 범위로 조회한다 |
| 계정과 보안 | 본사 | 내부 어드민 | 매장은 자기 비밀번호만 바꾼다 |
| 운영 | 본사 | 내부 어드민 | 매장은 접근하지 않는다 |

매출만 화면을 둘로 나눈다. 본사는 매장 간 비교로 어느 매장과 상권이 잘 되는지를 묻고, 매장은 시간과 메뉴로 무엇이 얼마나 팔렸는지를 묻는다. 같은 원본을 보지만 축이 다르다. 한 화면에 두 축을 넣으면 양쪽 모두 쓰기 어려워진다.

단말과 알림은 화면을 하나만 둔다. 두 주체가 같은 질문을 하고 같은 값을 본다. 범위와 할 수 있는 동작만 다르다.

## 9. 권한

역할과 데이터 범위를 분리한다. 역할은 무엇을 할 수 있는지만 정하고, 어느 매장이 보이는지는 조직 계층으로 판정한다.

| 역할 | 데이터 범위 | 주요 권한 |
| --- | --- | --- |
| 본사 운영자 | 전체 | 행사·상권·브랜드·매장 등록, 가맹 관리자 계정 발급, 전체 매출 조회, 정산 대사, 배치 실행 관리, 접속기록과 계정 변경 이력 점검, 개인정보 파기, 대행 접속, 연동 계정 관리 |
| 가맹 관리자 | 담당 매장 | 매점 정보 조회와 변경, 영업 상태 변경, 메뉴와 카테고리와 옵션과 판매가 관리, 표시 정보 입력, 품절 설정, 메뉴 가져오기, 주문 접수, 알림 발송 이력 확인, 담당 매장 매출 조회 |
| 고객 | 자기 주문 | 메뉴 조회, 주문, 결제, 주문번호와 휴대폰번호로 조회 |
| 외부 POS | 허용된 매장 | 매장·메뉴 조회 |

권한이 있다는 것과 특정 매장이 보인다는 것은 별개 통제다. 매장이 늘어날 때마다 권한 정의를 고치지 않도록 데이터 범위는 조직 계층으로 판정한다.

메뉴와 카테고리 생성은 매장이 한다. 본사는 메뉴를 만들지 않는다. 가맹 관리자 계정은 본사가 발급하고 담당 매장 범위를 지정한다.

## 10. 용어 정의

문서 전체에서 같은 뜻으로 쓴다.

| 용어 | 정의 |
| --- | --- |
| 행사 | 시작일과 종료일을 가진 운영 단위. 상설 매장은 종료일 없는 상시 행사에 속한다 |
| 상권 | 행사 안에서 매장을 묶는 지역 구분 단위 |
| 브랜드 | 카테고리와 메뉴를 소유하는 단위 |
| 매장 | 실제 판매가 일어나는 장소. 브랜드 하나에 속하고 지점번호를 갖는다 |
| 지점번호 | 브랜드 안에서 매장을 구분하는 일련번호. 1호점, 2호점이 여기에 해당한다 |
| 카테고리 | 메뉴를 묶는 관리용 분류 |
| 메뉴 | 판매 단위. 원산지와 알레르기 정보를 속성으로 갖는다 |
| 옵션 그룹 | 메뉴에 연결하는 선택 묶음 |
| 옵션 항목 | 옵션 그룹 안의 개별 선택지 |
| 매장별 메뉴 설정 | 매장과 메뉴를 잇는 연결 객체. 판매가, 노출 여부, 품절 상태를 담는다 |
| 본사 통제 | 매장에서 메뉴 설정을 바꿀 수 없는 상태 |
| 매장 통제 | 매장이 자기 매장의 판매가, 노출 여부, 품절 상태를 바꿀 수 있는 상태 |
| 주문서 | 매장 프린터로 출력하는 조리용 출력물 |
| 망취소 | 승인 결과를 판단할 수 없을 때 원 승인을 되돌리는 처리 |

주문 상태값은 접수 대기, 접수 완료, 조리 중, 조리 완료, 수령 완료, 취소를 쓴다. 취소는 접수 대기와 접수 완료에서만 가능하며, 접수 완료 후 1분이 지나면 조리 중으로 자동 전환되어 취소할 수 없다. 매장 상태값은 개설 준비, 영업, 일시중지, 종료, 폐점을 쓴다. 개설 준비는 가맹 관리자가 등록한 뒤 본사가 개시를 확정하기 전까지다. 종료는 재배치할 수 있고 폐점은 하지 않는다.

| 어드민 인증 | 외부에서 접속하는 모든 어드민 사용자에게 안전한 인증수단을 적용한다. 계정과 비밀번호만으로는 요건을 충족하지 않는다 |
| 접속기록 | 계정, 일시, 접속지, 처리한 정보주체, 수행업무를 남기고 1년 이상 보관하며 월 1회 점검한다. 대행 접속은 실제 조작자와 대상 계정을 함께 기록한다 |
| 거래기록 | 대금결제와 재화공급 기록을 5년간 보존한다 |
| 원산지 표시 | 모든 메뉴판에 표시한다. 모바일 메뉴판과 키오스크 화면도 대상으로 본다. 글자 크기는 메뉴 이름과 같거나 커야 한다 |
| 알레르기·영양성분 | 메뉴 단위로 등록하며 필수 입력이다. 법정 표시 의무는 브랜드의 직영과 가맹 합산 50개 이상일 때 발생하나 그와 무관하게 항상 받는다. 영양성분 의무 항목은 열량, 당류, 단백질, 포화지방, 나트륨 5종이다. 매장 메뉴판에서 열량은 식품명 또는 가격 활자 크기의 80퍼센트 이상으로 표시한다 |
| 키오스크 접근성 | 접근성 의무가 시행 중이다. 검증기준 준수 단말과 음성안내장치가 원칙이다 |
| 오프라인 결제 | 설계하지 않는다. 국내 VAN 승인은 온라인 실시간이 전제다 |
| 카드정보 | 저장하지 않는다. PG 인증결제와 서버 승인 구조를 쓴다 |
| 대금 수취 | 플랫폼이 대금을 수취하지 않는다. 카드 대금은 PG사와 카드사가 가맹점에 직접 지급한다 |
| 선불충전 | 도입하지 않는다. 포인트와 기프트 기능을 두지 않는다 |
| 회원 | 하이브리드 웹앱에 회원 개념을 두지 않는다. 모든 주문은 비회원 주문이다 |
| 주문자 개인정보 | 이름과 휴대폰번호를 주문 처리 목적으로만 쓴다. 수집 시 이용 목적과 보유 기간을 안내하고 동의를 받는다 |
| 메뉴 관리 | 매장이 자기 메뉴를 등록하고 관리한다. 본사는 메뉴를 만들지 않으며 배포 절차를 두지 않는다 |
