## 2. 적용 기준

조사에서 나온 문제를 항목별로 기준으로 확정한다. 남은 결정은 5절에 모은다.

### 2.1 계층 구조

선례가 없으므로 직접 정의한다.

| 계층 | 정의 | 판단 기준 |
| --- | --- | --- |
| 행사 | 시작일과 종료일을 가진 운영 단위. 그 기간에만 소속 매장이 열린다 | 종료일이 지나면 소속 매장을 자동으로 영업 종료로 전환한다 |
| 상권 | 행사 안에서 매장을 묶는 지역 구분 단위 | 통계 비교의 기본 축이다. 매장은 상권 하나에만 속한다 |
| 브랜드 | 메뉴와 카테고리를 소유하는 단위 | 같은 브랜드의 매장은 같은 메뉴를 쓴다 |
| 매장 | 실제 판매가 일어나는 장소 | 브랜드 하나에 속하고 그 안에서 지점번호를 갖는다 |

매장 표시명은 브랜드명과 지점번호를 조합한다. 1호점, 2호점이 지점번호에 해당한다.

직영과 가맹은 구분하지 않는다. 두 유형 사이에 메뉴, 가격, 권한의 정책 차이가 없다.

상설 매장은 종료일이 없는 상시 행사에 소속시킨다. 행사 개념을 우회하지 않고 하나의 구조로 처리한다.

상권은 전국 단위 표준 코드가 없다. 자체 코드로 관리하고 행정동 코드를 참조 항목으로 함께 보관한다. 외부 상권 데이터와 결합할 때 연결 고리가 된다.

#### 매장 식별

사업자등록번호를 매장 식별자로 쓰지 않는다. 법령상 유일성이 성립하지 않는다.

부가가치세법 시행령 제10조는 행사장에 개설한 임시사업장을 기존사업장에 포함되는 것으로 정한다. 한 사업자가 다섯 개 행사장에 부스를 내도 사업자등록번호는 하나다. 사업자단위과세의 종된사업장도 본점 번호를 공유한다.

매장에는 자체 식별자를 부여한다. 사업자등록번호는 운영 주체의 속성으로 보관하고, 국세청 상태조회로 휴폐업과 과세유형을 확인하는 용도로만 쓴다.

설치기간이 10일 이내면 임시사업장 개설신고를 하지 않을 수 있다. 매장 등록 화면에서 사업자 정보를 받되 중복을 저장 불가 사유로 삼지 않는다.

### 2.2 메뉴 마스터 제공 규격

업계는 POS가 기준이다. 본 서비스는 ERP가 기준이므로 제공 규격을 우리가 정의한다.

| 항목 | 기준 |
| --- | --- |
| 소유자 | 브랜드가 메뉴와 카테고리를 소유한다. 매장은 참조한다 |
| 생성 권한 | 메뉴와 카테고리 생성은 본사에서만 한다. 매장은 만들 수 없다 |
| 매장 권한 | 매장 통제로 지정된 매장은 자기 매장의 판매가, 노출 여부, 품절 상태만 바꾼다 |
| 외부 POS | 직접 등록·수정할 수 없다. 조회만 제공한다 |
| 제공 방식 | 조회 전용. 등록·수정 기능을 열지 않는다 |
| 제공 리소스 | 매장, 카테고리, 메뉴, 옵션 그룹, 옵션 항목 |
| 변경 통지 | 웹훅. 매장 식별자와 변경 시각만 보낸다. 상세는 조회하게 한다 |
| 증분 조회 | 변경 시각 기준 조회를 제공한다. 전량 재조회를 피한다 |
| 백업 폴링 | 최종 변경 시각 조회를 30분 주기로 허용한다 |
| 품절·일시중지 | 메뉴 전체 동기화와 분리해 항목 단위로 통지한다 |
| 인증 | 접근 키와 비밀 키. 매장 범위는 요청 헤더로 지정한다 |
| 멱등 | 이벤트 식별자로 중복을 걸러낸다. 2xx를 먼저 응답하고 비동기로 처리한다 |
| 버전 | 날짜 기반으로 표기한다. 신규 버전을 먼저 시험한 뒤 전환한다 |

### 2.3 표시 의무

의무는 세 갈래이고 대상 판정 기준이 서로 다르다. 하나의 설정으로 묶지 않는다.

| 구분 | 대상 판정 | 판정 단위 | 근거 |
| --- | --- | --- | --- |
| 원산지 | 영업 종류. 휴게음식점, 일반음식점, 위탁급식, 집단급식소 | 매장 | 원산지표시법 시행령 제4조 |
| 알레르기 | 가맹사업이고 직영과 가맹 합산 50개 이상 | 브랜드 | 어린이식생활안전관리특별법 시행령 제8조 |
| 영양성분 | 알레르기와 동일 | 브랜드 | 같은 조문 |

브랜드에 알레르기·영양성분 표시 대상 값을 두고, 매장에 원산지 표시 대상 값을 둔다. 원산지는 규모와 무관하게 대상이며 제과점영업만 제외된다.

팝업과 행사 매장에 예외를 두지 않는다. 표시 의무를 완화하는 규정이 없다. 완화되는 것은 시설기준과 영업신고 절차뿐이다.

#### 등록 항목

| 항목 | 기준 |
| --- | --- |
| 알레르기 | 메뉴 단위. 법정 19개 품목 중 선택한다. 자유 입력을 두지 않는다 |
| 알레르기 함량 | 입력란을 두지 않는다. 고시가 양과 관계없이 표시하도록 정한다 |
| 해당 없음 | 명시적으로 선택하게 한다. 미입력과 구분한다 |
| 옵션 알레르기 | 옵션 항목마다 별도로 입력받는다. 주문 화면에서 합집합으로 계산한다 |
| 영양성분 | 열량, 당류, 단백질, 포화지방, 나트륨 5종이다. 9종은 가공식품 기준이며 음식점에 적용되지 않는다 |
| 표시 기준량 | 총 내용량당, 100그램당, 단위 내용량당, 1회 섭취참고량당 중 선택해 함께 보관한다 |
| 세트 메뉴 | 총 열량을 별도로 받는다. 조합이 여럿이면 최소값과 최대값을 받는다 |
| 산출 근거 | 영양성분에 근거 자료를 첨부한다. 근거 없는 임의 표시는 과태료 대상이다 |
| 원산지 | 메뉴 단위. 법정 30개 품목 중 사용한 품목의 원산지를 입력한다 |
| 쇠고기 | 원산지와 별도로 식육의 종류를 받는다. 한우, 젖소, 육우로 구분한다 |
| 혼합 원산지 | 섞음 비율이 높은 순서로 입력한다. 순서 없는 복수 원산지는 저장하지 않는다 |

입력 필수 여부는 법정 대상 여부와 무관하게 항상 필수로 둔다. 나중에 대상이 되었을 때 과거 메뉴를 소급 입력하는 일을 피한다.

#### 화면 표시

구체 기준이 있는 것은 원산지뿐이다.

| 항목 | 원산지 | 알레르기·영양성분 |
| --- | --- | --- |
| 위치 | 제품명 또는 가격 옆, 위, 아래에 붙인다 | 제품명 또는 가격표시 주변 |
| 글자 크기 | 제품명 또는 가격과 같거나 커야 한다 | 기준 없음 |
| 글자색 | 제품명 또는 가격과 같은 색 | 바탕색과 구분되는 색상 |
| 표시 시점 | 제품이 화면에 나타나는 시점부터 | 기준 없음 |
| 별도 창 | 첫 화면에 그 위치를 알리는 표시를 둔다 | 기준 없음 |

키오스크도 같은 기준을 적용한다. 시행규칙 별표 4가 전자적 매체 메뉴판에 통신판매 기준을 적용할 수 있게 한다.

알레르기와 영양성분은 크기와 시점 기준이 없다. 원산지 기준을 준용해 설계한다. 상세 화면 하단이나 별도 탭에만 두는 구조는 근거가 약하다.

매장 메뉴판에서 열량은 식품명 또는 가격 활자 크기의 80퍼센트 이상으로 표시한다. 온라인 화면에는 이 기준이 없다.

#### 배달과 외부 채널

배달은 포장재에 원산지를 표시한다. 어려우면 전단지, 스티커, 영수증으로 대체한다.

영양성분은 온라인으로만 주문받아 배달하고 온라인으로 정보를 제공하면 리플릿 동봉을 생략할 수 있다. 채널마다 온라인 전용 여부를 두어 판정한다.

2026년 10월 22일부터 통신판매중개사업자에게 입점 사업자 대상 원산지 표시제도 고지 의무가 생긴다. 본 서비스는 중개가 아니므로 직접 대상이 아니다. 외부 채널 연동 시 상대의 요구가 늘어날 수 있다.

### 2.4 메뉴 반영

배포 절차를 두지 않는다. 매장이 저장하면 그 매장의 주문 채널에 반영된다.

| 항목 | 기준 |
| --- | --- |
| 관리 주체 | 매장. 본사는 메뉴를 만들지 않는다 |
| 저장과 반영 | 분리하지 않는다. 저장하면 반영된다 |
| 판매 조건 | 표시 정보가 입력되지 않은 메뉴는 판매 불가 상태로 둔다 |
| 반영 시점 | 웹앱은 즉시. 키오스크는 유휴 시점과 결제 완료 시점. 외부 POS는 통지 후 상대가 조회 |
| 변경 이력 | 변경 시각, 처리자, 변경 항목을 남긴다 |
| 영업 중 변경 | 진행 중 주문이 있으면 경고를 표시한다. 진행 건은 기존 가격으로 처리한다 |

조사한 상용 제품은 본사가 발행하고 매장이 받는 구조다. 본 서비스는 매장이 원본을 갖는다. 내려보낼 것이 없으므로 발행 개념이 성립하지 않는다.

### 2.5 결제 데이터

| 항목 | 기준 |
| --- | --- |
| 최상위 키 | 플랫폼 자체 결제 식별자를 쓴다. 채널별 식별자는 하위 항목으로 붙인다 |
| 공통 항목 | 승인번호는 PG와 VAN 공통으로 보관한다. 카드 승인번호는 최대 8자다 |
| 채널별 항목 | PG는 결제 키와 거래 키, VAN은 단말기번호와 거래일련번호를 보관한다 |
| 결제 상태 | 준비, 진행 중, 입금 대기, 완료, 취소, 부분취소, 중단, 만료 여덟 가지를 보관한다 |
| 매입 상태 | 준비, 요청, 완료, 취소 요청, 취소 다섯 가지를 결제 상태와 별도로 보관한다 |
| 부분취소 | 전체 금액과 취소 가능 잔액을 함께 보관한다. 두 값의 차이로 부분취소를 판정한다 |
| 취소 참조 | 취소 건마다 금액, 사유, 시각, 거래 키를 개별로 남긴다 |
| 매출 집계 | 채널을 통합해 집계한다 |
| 정산 | 통합하지 않는다. VAN 대금은 카드사가 가맹점에 직접 지급한다 |
| PG 처리 | 인증과 승인 사이에 서버가 금액을 검증한다. 검증 실패 시 승인을 호출하지 않는다 |
| 승인 유효 시간 | 인증 후 10분이다. 승인 경로에 외부 호출이나 긴 작업을 두지 않는다 |
| 멱등 | 헤더로 멱등키를 받는 곳은 토스페이먼츠뿐이다. 그 밖에는 주문번호 단위 잠금과 승인 상태 선점으로 대체한다 |
| 웹훅 | 순서를 가정하지 않는다. 수신 즉시 조회 API로 다시 확인한다. 일반 결제 웹훅에는 서명 수단이 없다 |
| 미승인 건 | 자동 취소 배치를 두지 않는다. 승인하지 않으면 결제 세션이 만료되어 결제가 성립하지 않는다 |
| 오프라인 결제 | 설계하지 않는다. 국내 VAN 승인은 온라인 실시간이 전제다 |

### 2.6 알림과 결제 복귀

| 항목 | 기준 |
| --- | --- |
| 주문 알림 | 카카오 알림톡을 주 경로로 한다. 실패 시 문자로 대체 발송한다 |
| 웹 푸시 | 사용하지 않는다. iOS는 브라우저 탭에서 받을 수 없다 |
| 결제 복귀 | 복귀 주소 수신, 웹훅 수신, 서버 조회 세 경로를 함께 둔다 |
| 결과 유실 | 복귀 결과가 없으면 서버가 결제 상태를 조회한다. 그래도 판단이 안 되면 웹훅을 기다린다 |
| 주문 상태 | 서버에서 조회한다. 브라우저 저장소에 의존하지 않는다 |

### 2.7 결제·정산 계약 구조

외부 결제대행사가 정산을 전담하고 플랫폼은 정산에 필요한 정보만 제공한다. 금융위원회가 2024년 6월 보도설명자료에서 등록이 필요 없는 사례로 명시한 구조다.

플랫폼은 대금을 수취하지 않는다. 자금이 플랫폼 계좌를 경유하거나 플랫폼이 매장별 정산금액을 계산해 집행하면 등록 대상이 된다. 플랫폼 명의 수납 계좌를 두지 않는 것을 설계 제약으로 못 박는다.

각 매장을 결제대행사의 하위가맹점으로 등록한다. 대표가맹점은 등록 결제대행사가 맡고 플랫폼은 대표가맹점이 되지 않는다. 조건은 셋이다.

1. 대표가맹점 지위를 갖는 자가 등록 결제대행사여야 한다. 선불과 직불 영역은 2025년 9월 15일부터 법정 의무다.
2. 실제 재화와 용역을 제공한 가맹점 정보를 이용자가 알 수 있게 해야 한다.
3. 세무자료 제출 주체가 등록 결제대행사다. 매출은 실제 가맹점에 귀속된다.

매장별 사업자등록번호와 정산계좌를 매장 마스터의 필수 항목으로 관리한다. 하위가맹점 심사 완료를 주문 개시 조건으로 둔다. 행사와 상권 계층은 내부 운영 단위로만 쓰고 결제와 정산 계층에는 매장만 노출한다.

2026년 12월 17일에 개정 전자금융거래법이 시행된다. 정의에 제3자 사이라는 문구가 명시되어 자기 사업 내부정산을 배제한다. 무수취 구조는 개정 후에도 등록 대상이 아니다. 다만 정산대상금액 전액을 외부에서 관리하는 의무가 신설되므로, 플랫폼이 대금을 수취하는 기능을 나중에 추가하면 그 의무까지 함께 걸린다.

자금과 정보의 흐름은 다음과 같다.

```arch
== 거래 ==
[고객]
행위: 주문, 결제
[매장]
행위: 조리, 제공
== 결제와 정산 ==
[아이오더 플랫폼]
역할: 주문과 결제 정보 제공
[결제대행사]
역할: 승인 중계, 대금 정산
[카드사]
역할: 승인, 대금 지급, 청구
@ 고객 -> 매장 : 주문과 수령
@ 고객 -> 결제대행사 : 결제 요청
@ 결제대행사 -> 카드사 : 승인 요청
@ 카드사 -> 결제대행사 : 대금 입금
@ 결제대행사 -> 매장 : 대금 입금. 수수료를 뺀 금액
@ 매장 => 결제대행사 : 결제 수수료
@ 카드사 => 고객 : 결제대금 청구와 수납
@ 아이오더 플랫폼 => 결제대행사 : 매장 계좌와 주문 정보
@ 결제대행사 => 아이오더 플랫폼 : 승인 결과와 정산 내역
!플랫폼은 자금 경로에 없다. 정보만 제공한다. 이 구조라서 전자지급결제대행업 등록 의무가 없다.
!점선은 정보와 청구의 흐름이고 실선은 자금과 승인의 흐름이다.
!정산 내역은 대사에만 쓴다. 플랫폼이 매장별 정산금액을 계산하지 않는다.
```

선불충전은 도입하지 않는다. 업종 기준이 폐지되어 두 매장 이상에서 쓰이면 선불전자지급수단에 해당한다. 등록 면제는 발행잔액 30억원 미만이면서 연간 총발행액 500억원 미만인 경우에만 적용된다. 두 요건을 모두 충족해야 한다. 선불충전금 전액 별도관리 의무에는 유예가 없다.

| 대행 접속 | 본사가 가맹 화면을 대신 볼 때 실제 조작자와 대상 계정을 함께 기록한다 |
| 권한 구조 | 역할과 데이터 범위를 분리한다. 범위는 조직 계층으로 판정한다 |

### 2.9 회원 체계

하이브리드 웹앱에 회원 개념을 두지 않는다. 모든 주문을 비회원 주문으로 처리한다.

| 항목 | 기준 |
| --- | --- |
| 로그인 | 없다. 주문에 계정이 필요하지 않다 |
| 주문자 정보 | 이름과 휴대폰번호를 입력받는다 |
| 주문 조회 | 주문번호와 휴대폰번호 조합으로 조회한다 |
| 알림 발송 | 입력받은 휴대폰번호로 알림톡을 보낸다 |
| 개인정보 | 이름과 휴대폰번호를 주문 처리 목적으로만 쓴다. 수집 시 이용 목적과 보유 기간을 안내하고 동의를 받는다 |
| 보유 기간 | 거래기록 보존 기간을 따른다. 대금결제와 재화공급 기록은 5년이다 |

쿠폰과 포인트를 두지 않으므로 회원 식별이 필요한 기능이 없다.

| 채널별 수단 | 하이브리드 웹앱은 결제대행사 결제창, 키오스크는 현장 카드 단말을 쓴다 |
| 현금영수증 | 현금을 받지 않으므로 발행 화면을 두지 않는다 |
| 호출 순번 | 주문 확정 시점에 매장별로 부여한다. 매일 1번부터 다시 시작한다 |
| 순번과 주문번호 | 순번은 현장에서 부르는 번호다. 주문 조회와 대사에는 주문번호를 쓴다 |

### 2.11 상권 통계

제품 내장 기능이 없으므로 자체 집계로 만든다. 행사와 상권 단위로 진행 중 매출을 비교하는 기능은 국내에서 확인된 사례가 없다.

#### 집계

| 항목 | 기준 |
| --- | --- |
| 집계 축 | 행사, 상권, 브랜드, 매장, 채널, 결제수단, 기간 |
| 집계 방식 | 야간 배치로 집계 테이블을 만든다. 당일 구간은 운영 데이터에서 조회한다 |
| 적재 시점 | 집계 테이블은 주문이 발생하는 시점부터 함께 적재한다. 나중에 만들면 과거 구간이 빈다 |
| 시작 시점 | 주문이 발생하는 단계에서 함께 시작한다. 나중에 만들면 과거 구간이 빈다 |

#### 비교 지표

행사 기간과 매장 수가 다르므로 총매출만으로는 비교가 되지 않는다. 세 지표를 함께 낸다.

| 지표 | 산식 | 용도 |
| --- | --- | --- |
| 매장·일 평균 매출 | 총매출 ÷ (매장 수 × 운영일수) | 상권 간 1차 비교 |
| 객수 | 결제 건수 | 매출 변화의 원인 분해 |
| 객단가 | 매출 ÷ 결제 건수 | 같음 |

맥도날드와 스타벅스가 동일점포매출을 객수와 객단가로 나눠 공시하는 방식을 따른다. 어느 상권이 잘 팔린다는 것이 사람이 많아서인지 많이 사서인지 구분해야 다음 행사 구성에 반영할 수 있다.

매장당 평균 매출을 낼 때 영업일수를 지표 정의 안에서 제거한다. Noodles and Company는 매출을 그 기간의 영업일수로 나눈 뒤 표준 영업일수를 곱해 환산한다. 같은 방식으로 매장 수와 운영일수를 모두 분모에 넣는다.

운영일수가 지나치게 짧은 매장은 평균을 왜곡한다. 최소 운영일수를 정해 그에 못 미치는 매장을 평균 산정에서 제외하고, 제외한 매장 수를 함께 표시한다. Wingstop이 개점 52주 이상 매장만으로 평균을 내는 것과 같은 취지다.

요일 구성 차이를 보정한다. 맥도날드는 요일과 휴일 구성의 영향을 별도 조정 항목으로 공시하며, 그 영향이 기간이 짧을수록 크다고 밝힌다. 행사는 1~2주다. 주중과 주말을 분리해 집계하고 같은 요일 유형끼리 비교한다.

입장객 수를 확보할 수 있는 행사에 한해 1인당 지출을 부가 지표로 제공한다. 확보하지 못하는 행사가 많으므로 필수 지표로 두지 않는다.

1인당 지출은 방문객 구성에 따라 크게 갈린다. 한국관광공사가 문화관광축제 62개를 분석한 결과 전체 평균은 32,415원이나 외지인은 53,951원, 현지인은 1,480원이다. 36배 차이다. 구성을 나누지 않은 값은 해석하기 어렵다. 구성 정보를 받을 수 있으면 나눠서 제공한다.

1인당 지출을 낼 때 분모의 단위를 밝힌다. 전시 산업 감사 규칙은 방문객과 방문을 구분한다. 방문객은 행사 전 기간에 한 번만 세고, 방문은 하루에 한 번 센다. 방문객 기준은 개최일수에 거의 영향받지 않고 방문 기준은 일수에 비례한다. 어느 단위로 받은 값인지 모르면 행사 간 비교가 성립하지 않는다.

기상 보정은 초기 범위에서 다루지 않는다. 소매와 외식 기업 중 날씨 영향을 수치로 분리해 공시한 사례가 확인되지 않는다. 제도화된 곳은 전력업계뿐이다. 근거 없이 보정하면 판단을 흐린다.

#### 잠정치와 확정치

당일 수치가 바뀌는 것은 정상이다. 카드 매출전표 제출 기한이 승인일부터 30일이고 매입취소는 사흘가량 걸린다. 정산은 영업일 기준이므로 주말과 공휴일이 끼면 더 늦다.

| 항목 | 기준 |
| --- | --- |
| 상태 | 매출 레코드에 잠정과 확정을 두고 확정 시각을 함께 보관한다 |
| 화면 표기 | 잠정치를 숨기지 않는다. 주석이 아니라 숫자 옆에 표시한다 |
| 확정 전환 | 배치로 처리하고 전환 시 원래 수치와의 차이를 보관한다 |
| 진행 중 판단 | 잠정치 기준으로 화면을 만든다. 확정을 기다리면 행사가 끝난다 |
| 취소 반영 | 매입 후 취소는 취소 일자에 별도 거래로 기록한다. 원거래 일자로 소급하지 않는다 |
| 승인취소 | 매입 전 취소는 원거래가 매출로 확정되지 않는다. 매출에서 제외한다 |

한국은행은 속보치와 잠정치 사이에 7주 간격을 두고, 개정 사유를 기간 마지막 구간의 실적자료 미확보로 설명한다. 행사 매출도 같은 구조다.

국가데이터처 소매판매액지수는 최근 2개월을 잠정치로 두고 보도자료 표지에 그 사실을 밝힌다. 연쇄지수 특성상 매년 초에 직전연도 수치가 한 번 더 수정된다. 공표 자료에서도 수정 경로가 두 갈래다.

#### 데이터 완전성

행사장에는 현금만 받는 부스가 실재한다. 본 서비스는 현금을 받지 않으므로 그런 매장의 매출은 플랫폼에 들어오지 않는다.

플랫폼 밖 현금 매출을 입력받지 않는다. 대신 주문 채널을 쓰지 않는 매장을 상권 비교에서 제외 대상으로 표시한다. 일부만 집계된 수치를 전체인 것처럼 보여주지 않는다.

#### 외부 데이터 결합

초기 범위에서 제외한다. 공공 상권 체계로는 요구를 충족하지 못한다.

건물 내부의 층과 구역을 표현할 수 없다. 공공 상권의 최소 단위는 골목상권 수준의 면적 구역이다. 서울 밖에는 전국 단위 상권 경계 파일이 없다. 갱신도 분기 단위이거나 비정기여서 진행 중 판단에 쓸 수 없다.

상권 마스터에 자체 코드를 두고 중심좌표, 폴리곤, 행정동코드, 서울 상권코드를 부가 필드로 관리한다. 서울 지역은 공개된 상권 경계 파일과 공간 교차로 연결하고, 그 밖의 지역은 행정동코드까지만 연결한다. 공공 데이터는 사후 대조용이지 운영 지표가 아니다.

### 2.12 관리 주체

본사와 매장이 다루는 대상을 나눈다. 같은 대상을 둘이 함께 고치지 않는다.

| 대상 | 본사 | 매장 |
| --- | --- | --- |
| 행사, 상권, 브랜드 | 관리 | 조회 불가 |
| 매장 등록과 상태 | 관리 | 변경 요청만 |
| 가맹 관리자 계정 | 발급 | 불가 |
| 카테고리, 메뉴, 옵션 | 불가 | 관리 |
| 판매가 | 불가 | 관리 |
| 알레르기, 원산지, 영양성분 | 불가 | 관리 |
| 품절 | 불가 | 관리 |
| 매출 조회 | 전체 매장 | 담당 매장 |
| 외부 연동 계정 | 관리 | 불가 |

가맹 어드민에 회원가입을 두지 않는다. 본사가 계정을 발급하고 담당 매장 범위를 지정한다.

표시 정보를 매장이 관리하므로 입력 책임도 매장에 있다. 미입력 메뉴는 판매할 수 없게 막아 누락이 운영으로 넘어가지 않게 한다.

### 2.13 품절 처리

품절로 설정한 메뉴는 주문 채널에서 노출하지 않는다.

| 항목 | 기준 |
| --- | --- |
| 노출 | 품절 메뉴는 목록에 표시하지 않는다. 담기 차단이나 품절 표시를 쓰지 않는다 |
| 반영 시점 | 웹앱은 즉시. 키오스크는 유휴 시점과 결제 완료 시점 |
| 설정 주체 | 본사와 매장 모두 설정한다. 뒤에 설정한 값이 적용되고 처리자를 기록한다 |
| 재개 | 재개 예정 시각을 지정하면 그 시각에 자동으로 노출된다 |
| 장바구니 | 담은 뒤 품절되면 장바구니에서 해당 항목을 제거하고 사용자에게 알린다 |
| 외부 POS | 품절 통지를 별도 경로로 보낸다. 상대가 노출을 제어한다 |

조사한 상용 제품은 품절 메뉴를 표시하고 선택만 막는 방식과 목록에서 제외하는 방식을 모두 제공한다. 본 서비스는 제외로 통일한다. 행사 매장은 회차마다 품절이 잦아 표시된 메뉴를 선택했다가 막히는 경험이 반복되면 주문 속도가 떨어진다.

### 2.14 계정 정책

가맹 어드민에 회원가입을 두지 않는다. 본사가 계정을 발급한다. 그래서 잃어버렸을 때의 복구 경로를 반드시 둔다.

| 항목 | 기준 |
| --- | --- |
| 발급 | 본사가 아이디, 이름, 연락처, 권한, 담당 매장 범위를 지정해 만든다 |
| 초기 비밀번호 | 등록한 휴대폰번호로 보낸다. 첫 로그인 시 변경을 강제한다 |
| 재설정 | 아이디와 등록된 휴대폰번호로 본인을 확인한 뒤 인증번호를 보낸다 |
| 재설정 안내 | 아이디와 휴대폰번호 중 어느 쪽이 틀렸는지 밝히지 않는다 |
| 로그인 실패 | 연속 5회 실패하면 계정을 잠근다. 성공하면 횟수를 초기화한다 |
| 실패 안내 | 남은 횟수를 함께 보여준다. 갑자기 잠기지 않게 한다 |
| 잠금 해제 | 매장 계정은 비밀번호 재설정을 마치면 자동으로 풀린다. 본인 확인을 거치기 때문이다 |
| 본사 해제 | 본사가 계정 목록에서 직접 풀 수 있다. 사유를 남긴다 |
| 본사 계정 | 본사 계정이 잠기면 다른 본사 운영자가 푼다. 전원이 잠기는 상황을 막기 위해 본사 계정은 둘 이상 유지한다 |
| 인증 실패 제한 | 재설정 과정의 인증번호 실패가 이어지면 일정 시간 차단하고 본사 문의로 안내한다 |
| 이전 값 | 직전 비밀번호와 같은 값으로 바꾸지 못한다 |
| 변경 기록 | 계정, 시각, 접속 주소, 처리 방식을 남긴다 |
| 권한 변경 | 권한과 담당 매장 범위를 바꾸면 변경 전후 값을 별도 이력으로 남긴다 |

잠금 해제를 두 경로로 둔다. 매장이 스스로 풀 수 있어야 야간과 주말에 영업이 멈추지 않고, 본사 해제를 남겨야 재설정 경로까지 막힌 경우를 처리할 수 있다.

권한 변경을 접속기록과 분리한다. 접속기록은 누가 들어왔는지를 남기고, 계정 변경 이력은 누가 누구의 권한을 바꿨는지를 남긴다. 두 질문이 다르다.

### 2.15 표시 정보 책임

알레르기와 영양성분, 원산지는 메뉴를 등록한 매장이 입력하고 그 내용에 책임을 진다.

| 항목 | 기준 |
| --- | --- |
| 입력 주체 | 매장 |
| 입력 시점 | 메뉴 등록 시. 법정 의무 대상 여부와 무관하게 받는다 |
| 미입력 처리 | 판매 불가 상태로 두고 주문 채널에 노출하지 않는다 |
| 검증 | 시스템이 필수 항목 누락만 막는다. 값의 사실 여부는 검증하지 않는다 |
| 본사 관여 | 두지 않는다 |
| 책임 | 표시 내용의 정확성은 매장에 있다. 가맹 계약서에 명시한다 |

본사 검수 절차를 두지 않는다. 행사 개시 전 며칠 사이에 수백 건이 몰리고, 본사가 원산지의 사실 여부를 확인할 방법이 없다. 확인하지 못하는 것을 확인한 것처럼 기록하면 책임 소재만 흐려진다.

대신 매장이 입력을 빠뜨리지 못하게 막는다. 미입력 메뉴는 저장은 되지만 팔리지 않는다.

### 2.16 메뉴 가져오기

매장이 메뉴 원본을 가지므로 행사가 바뀔 때마다 다시 등록하게 된다. 가져오기로 그 부담을 줄인다.

| 항목 | 기준 |
| --- | --- |
| 대상 | 같은 사업자의 이전 매장, 같은 브랜드의 다른 매장 |
| 범위 | 카테고리, 메뉴, 옵션 구성, 알레르기, 원산지 |
| 제외 | 판매가. 매장마다 다르므로 복사하지 않는다 |
| 중복 | 같은 이름이 있으면 덮어쓰기와 건너뛰기 중 고르게 한다 |
| 판매가 미입력 | 판매 불가 상태로 저장한다 |
| 기록 | 원본 매장, 대상 건수, 처리자, 시각을 남긴다 |

조사한 상용 제품은 복사보다 버전 생성을 권장한다. 복사가 리포팅에서 중복 항목을 만들기 때문이다. 다만 버전은 상위 소유자와 하위 대상이라는 계층이 있어야 성립한다. 본 서비스는 매장이 원본을 가지므로 그 축이 없다.

같은 구조를 가진 제품은 실제로 값 복사를 제공한다. Square의 메뉴 복제는 복제본이 원본과 독립적으로 동작하고, 토스플레이스의 상품 불러오기도 값 복사다. 원본 연결을 유지하는 Olo와 Lightspeed는 모두 본사 마스터 모델이다.

Lightspeed는 반대 사례다. 상품을 공유 상태로 바꾸면 되돌릴 수 없고 원본 매장에서만 수정할 수 있게 된다. 연결을 만들면 해제 경로를 함께 설계해야 하고, 설계하지 못하면 매장 자율성이 영구히 사라진다.

복사한 메뉴는 원본과 연결하지 않고 독립된 값으로 둔다. 원본 매장이 바뀌어도 따라가지 않는다.

리포팅 중복은 실재하는 위험이므로 보완한다.

| 보완 | 내용 |
| --- | --- |
| 브랜드 집계 축 | 원본의 브랜드 메뉴 식별자를 함께 복사한다. 매장 메뉴 코드와 별개로 브랜드 단위 집계에 쓴다. 값만 물려받고 수정은 연동하지 않는다 |
| 표시 정보 | 복사한 알레르기와 원산지는 검수 대기로 둔다. 매장이 확인해야 판매 가능 상태가 된다 |
| 노출 순서 | 카테고리와 옵션의 정렬 순서를 함께 복사한다 |

원산지는 매장과 시기에 따라 달라진다. 복사한 값을 그대로 판매에 쓰면 표시가 사실과 어긋날 수 있다.

### 2.17 개인정보 파기

보유 기간만 정하고 지우는 절차가 없으면 기간 이상 보유하게 된다.

| 판정 | 주문 종결일부터 보유 기간이 지난 건 |

| 방법 | 복원할 수 없는 방법으로 처리한다 |

파기해도 매출은 유지된다. 개인 식별 항목만 지우고 거래 기록은 남긴다.

### 2.20 매장 수명주기

행사가 끝나면 매장을 철수하고 다음 행사에 다시 배치한다. 이 구조에서 상태와 소속을 어떻게 다룰지 정한다.

#### 상태값

기존 세 값에 폐점을 더해 넷으로 나눈다. 운영자가 수시로 바꾸는 값과 마스터 데이터 상태값을 한 필드에 두면 리포트 제외 기준이 흔들린다.

| 상태 | 의미 | 주문 | 리포트 |
| --- | --- | --- | --- |
| 영업 | 운영 중 | 접수 | 포함 |
| 일시중지 | 매장이 임시로 중단 | 차단 | 포함 |
| 종료 | 행사 종료로 철수. 다음 행사에 재배치 가능 | 차단 | 포함 |
| 폐점 | 영구 종료. 재배치하지 않는다 | 차단 | 기본 제외. 필터로 포함 |

Olo가 주문 일시 중단, 일시 폐점, 영구 폐점을 각각 다른 값으로 두는 것과 같은 이유다.

#### 삭제하지 않는다

매장을 지우지 않는다. 조사한 8개 제품 중 삭제가 가능한 것은 하나뿐이고, Square와 Olo는 거래 데이터 보존을 이유로 삭제를 명시적으로 막는다.

법령도 삭제를 막는다. 부가가치세법 제71조 제3항이 장부와 세금계산서를 확정신고 기한 후 5년, 국세기본법 제85조의3 제2항이 장부와 증거서류를 법정신고기한 후 5년, 전자상거래법 시행령 제6조가 대금결제와 재화 공급 기록을 5년 보존하도록 정한다. 폐업으로 이 의무가 사라진다는 규정은 없다.

폐점 매장은 목록 기본 조회에서 숨기고 필터로만 노출한다. 매장 코드는 재사용하지 않는다. 같은 장소에 다시 열어도 새 코드를 부여한다. 재사용하면 과거 매출이 새 매장에 섞인다.

#### 소속 변경과 매출 귀속

매장이 다른 행사나 상권으로 옮겨가도 과거 주문의 귀속을 바꾸지 않는다.

| 항목 | 기준 |
| --- | --- |
| 저장 | 주문에 발생 시점의 행사, 상권, 브랜드를 값으로 복사해 둔다 |
| 소속 이력 | 매장에 행사, 상권, 유효 시작일, 유효 종료일을 이력으로 남긴다 |
| 적용 시점 | 소속 변경은 변경일부터 적용한다. 소급하지 않는다 |
| 조회 기준 | 기본은 주문 시점 소속. 현재 소속 기준 재집계를 선택할 수 있다 |
| 화면 표기 | 어느 기준으로 조회했는지 표시한다. 두 값이 다를 수 있음을 알린다 |

근거는 넷이다.

첫째, Toast는 메뉴의 매출 분류를 바꾸면 이후 리포트에만 반영되고 이미 만들어진 리포트는 바뀌지 않는다고 명시한다. 그룹 재배치에 대한 서술은 어느 제품에도 없어 인접 문제의 원칙을 준용했다.

둘째, 덮어쓰기 방식은 이력을 파괴한다. 행사가 끝난 뒤 상권 배치를 조정하면 종료된 행사의 상권별 실적이 사후에 바뀐다. 목표 GO-02가 성립하지 않는다.

셋째, 국가데이터처는 행정구역이 바뀌어도 원 통계표를 덮어쓰지 않고 기준 시점별 재집계본을 병렬로 제공한다. 소급이 원칙인 것은 측정 방법 자체가 바뀐 경우다. 매장 소속 변경은 분류 축의 변경이다.

넷째, 이 문서가 이미 같은 원칙을 쓰고 있다. 주문 항목은 주문 시점의 메뉴와 단가를 보관하고, 취소는 원거래 일자로 소급하지 않는다.

다만 비교 목적의 재집계 요구는 수용한다. IFRS 8 문단 29는 보고부문 구성이 바뀌면 과거 기간을 재작성하도록 하고, 문단 30은 재작성하지 않으면 신 기준과 구 기준을 함께 공시하도록 한다. 그래서 두 기준을 모두 제공하고 어느 쪽으로 봤는지 화면에 남긴다.

이 항목은 참고할 제품 사례를 찾지 못했다. 회계기준과 공공 통계 처리 원칙을 준거로 삼아 정했다.

### 2.21 정산 대사

대사는 세 단계로 나눈다.

| 단계 | 맞추는 대상 | 주기 |
| --- | --- | --- |
| 거래대사 | 우리 결제 원장과 결제대행사 거래 내역 | 일 단위 |
| 정산대사 | 거래 내역과 정산 내역 | 일 단위 |
| 입금대사 | 정산 내역과 실제 입금액 | 지급일 기준 |

| 항목 | 기준 |
| --- | --- |
| 조인 키 | 결제 키와 주문번호를 쓴다. 승인번호는 보조 키다 |
| 조회 기준일 | 거래대사는 승인일, 정산대사는 정산 매출일을 기준으로 한다 |
| 취소 처리 | 승인과 취소를 상계하지 않고 개별로 조회한다. 부분취소와 익일취소가 있으면 상계 조회로는 원장과 맞지 않는다 |
| 매입 구분 | 매입 상태를 따로 보관해 매입 지연과 매입 실패를 승인 성공과 구분한다 |
| 미정산 | 정산 지급일이 도래하지 않은 건은 미정산으로 분류한다 |
| 정산 예정일 | 플랫폼이 추정하지 않는다. 결제대행사가 내려주는 지급일을 그대로 표시한다 |
| 조회 방식 | 대사 API는 등록된 서버 주소에서만 쓸 수 있고 1만 건 제한이 있다. 행사 규모가 커지면 파일 수신 방식으로 바꾼다 |

정산 주기는 공개 표준값이 없다. 카드 정산은 결제대행사와 카드사가 체결한 입금주기를 따른다. 여신전문금융업법에도 지급 기한 규정이 없다. 계약 사항이다.

#### 결제대행사 계약 시 확인할 것

| 항목 | 확인 내용 | 정해지지 않으면 |
| --- | --- | --- |
| 정산 주기 | 결제수단별 주기와 지급일 산정 방식 | 매장에 정산 예정일을 안내할 수 없다 |
| 정산 조회 | 제공 여부, 응답 항목, 조회 기준일 선택 가능 여부 | 정산대사를 자동화할 수 없다 |
| 대사 자료 | API와 파일 중 무엇을 제공하는지, 건수 제한 | 행사 규모가 커지면 대사가 막힌다 |
| 하위가맹점 | 매장 단위 등록 절차와 심사 기간 | 매장 개설부터 주문 개시까지의 기간을 잡을 수 없다 |
| 웹훅 | 이벤트 종류, 재전송 정책, 서명 제공 여부 | 결과 유실 대응을 설계할 수 없다 |
| 멱등 | 헤더 지원 여부와 유효 기간 | 중복 승인 방지 방식이 달라진다 |
| 부분취소 | 지원 여부와 처리 방식 | 부분 환불 기능을 넣을 수 없다 |

계약 전에는 확인되지 않은 항목을 가정하지 않는다. 정산 예정일은 결제대행사가 내려주는 값을 그대로 표시하고, 대사는 API와 파일 두 방식을 모두 받을 수 있게 설계한다.

### 2.22 VAN 처리 기준

망취소는 법령 용어가 아니다. VAN사 기술 규격상의 용어이므로 발동 조건과 재시도 정책을 연동 대상 VAN사 규격서로 확정한다.

공개 문서에서 확인된 발동 조건은 셋이다.

| 조건 | 내용 |
| --- | --- |
| 읽기 시간 초과 | 승인 요청 후 설정한 시간 안에 응답이 오지 않는다 |
| 연결 오류 | 승인 요청 중 연결이 끊기거나 네트워크 오류가 난다 |
| 응답 해석 실패 | 응답은 받았으나 형식이 깨져 성공 여부를 판단할 수 없다 |

프린터 오류와 전표 출력 실패는 망취소 조건이 아니다. 출력 실패는 재출력으로 처리하고 결제를 취소하지 않는다.

망취소는 승인번호를 쓰지 않는다. 승인 결과를 받지 못한 상태이므로 단말기번호, 거래일련번호, 금액, 거래일시로 원거래를 식별한다. 네 값을 승인 요청 시점에 저장한다.

무서명 5만원 기준은 여신전문금융업감독규정 제24조의6 제2항이 근거다. 카드사 자율 정책이 아니다. 거래금액이 5만원 이하이고 카드사가 부정사용 책임을 부담하기로 가맹점에 통지한 경우에만 본인확인을 생략할 수 있다. 2007년 이후 금액 기준이 바뀐 적이 없으며 2026년 5월 시행 현행 규정에서도 같다.

키오스크 서명 입력은 5만원 초과 거래에서 요구한다. 카드사 통지가 전제이므로 VAN사 계약 시 무서명거래 적용 여부를 확인한다.

#### 우리 쪽에서 정하는 것

VAN사 규격에 맡길 수 없는 항목은 우리가 정한다.

| 항목 | 기준 |
| --- | --- |
| 망취소 재시도 | 3회까지. 간격은 1초, 3초, 5초 |
| 재시도 실패 | 주문을 만들지 않고 거래를 보류로 기록한다 |
| 보류 거래 처리 | 매장 관리자 모드의 거래내역에 표시한다. 대사에서 확인한다 |
| 화면 안내 | 승인 여부를 알 수 없을 때 결제되지 않았다고 단정하지 않는다. 확인 중으로 표시하고 직원 호출을 안내한다 |
| 승인 대기 시간 | 30초. 초과하면 망취소 조건으로 본다 |

승인 여부를 모르는 상태에서 결제 실패로 안내하면 고객이 다시 결제해 이중 청구가 생긴다. 확인 중으로 두고 사람이 개입하게 한다.

#### VAN사 계약 시 확인할 것

| 항목 | 확인 내용 |
| --- | --- |
| 망취소 규격 | 발동 조건, 재시도 허용 횟수, 시간 제한 |
| 무서명거래 | 카드사 통지 여부와 적용 금액 |
| 단말 연동 | 통신 방식, 응답 시간, 오류 코드 체계 |
| 거래 식별 | 단말기번호와 거래일련번호의 채번 규칙 |
| 대사 자료 | 제공 방식과 항목 |

### 2.23 단말 관리

단말을 등록하는 주체와 장애 때 멈추는 주체를 나눈다.

| 항목 | 기준 |
| --- | --- |
| 등록·수정·삭제 | 매장이 한다. 본사는 하지 않는다 |
| 연결 방식 | 매장이 발급한 연결 코드를 단말에 입력한다. 유효시간 10분 |
| 본사 권한 | 전체 조회와 사용 중지, 사용 재개까지 한다 |
| 사용 중지 사유 | 본사가 중지할 때 사유를 필수로 입력한다 |
| 재개 주체 | 중지한 쪽이 재개한다. 본사가 중지한 단말은 매장이 풀 수 없다 |
| 통지 | 본사가 중지하면 매장에 통지한다 |
| 기록 | 조작자, 시각, 사유, 대상 단말을 남긴다 |

본사에 사용 중지 권한을 두는 이유는 장애 대응이다. 오작동하는 단말이 주문을 계속 받으면 고객 결제가 쌓인 채 처리되지 않는다. 매장에 연락이 닿지 않는 시간대가 있으므로 본사가 직접 멈출 수 있어야 한다.

재개를 중지한 쪽으로 묶는 이유는 대응의 실효성이다. 본사가 장애로 막은 단말을 매장이 바로 풀면 중지가 의미를 잃는다.

### 2.24 이상 알림

대시보드는 알림을 대체하지 않는다. 화면에만 두면 운영자가 열어볼 때까지 모른다.

보낼 대상을 고르는 기준은 하나다. 받는 사람이 취할 구체적 조치가 있는가.

| 이상 유형 | 본사가 할 수 있는 조치 | 판단 |
| --- | --- | --- |
| 단말 미연결 | 매장 연락, 사용 중지 처리, 다른 채널 안내 | 보낸다 |
| 접수 지연 | 없다. 매장이 처리한다 | 화면에만 둔다 |
| 매출 급락 | 특정되지 않는다. 한산한 경우와 구분되지 않는다 | 화면에만 둔다 |
| 품절 급증 | 없다. 매장의 운영 판단이다 | 화면에만 둔다 |

#### 발송 기준

| 항목 | 기준 |
| --- | --- |
| 1단계 | 단말 미연결 30분. 해당 매장에 보낸다 |
| 2단계 | 미연결 60분. 본사에 보낸다. 1단계 후에도 풀리지 않은 건만 해당한다 |
| 반복 | 단말당 단계별 1회. 해소될 때까지 다시 보내지 않는다 |
| 묶음 | 같은 행사에서 5분 안에 3건 이상 발생하면 건별로 보내지 않고 한 건으로 묶는다 |
| 시간대 | 행사 영업시간 안에만 보낸다. 영업 종료 후 발생 건은 다음 개시 30분 전에 묶어서 보낸다 |
| 경로 | 알림톡. 실패 시 문자로 대체한다 |
| 내용 | 매장명, 단말 종류, 미연결 경과 시간, 조치 방법을 담는다 |

#### 근거

산업 경보 기준 EEMUA 191은 정상 운영 중 운영자 1명당 10분에 1건을 넘지 않도록 권고한다. 시간당 6~12건을 넘으면 대응 품질이 떨어지고 중요한 건을 놓친다. 행사장에 단말이 140대 있으면 네트워크 장애 한 번에 수십 건이 동시에 발생한다. 묶음 발송을 두는 이유다.

먼저 매장에 보내는 이유는 조치할 수 있는 사람에게 먼저 가야 하기 때문이다. 프린터 용지나 전원처럼 현장에서 1분이면 푸는 건이 대부분이다. 본사가 먼저 받으면 결국 매장에 다시 연락하게 된다.

야간 발송은 법으로 막혀 있지 않다. 광고성 메시지만 21시부터 다음 날 8시까지 제한되고 거래와 서비스 이용에 필요한 정보성 메시지는 해당하지 않는다. 그래도 영업시간 안으로 제한한다. 영업이 끝난 뒤에는 받아도 할 수 있는 일이 없다.

조사 근거는 `research/이상알림_조사.md`에 있다.

### 2.25 운영 동선

본사 운영자의 일은 행사 단위로 시작하고 끝난다. 메뉴는 업무 영역으로 나뉘어 있지만 실제 작업은 행사 하나를 두고 여러 영역을 오간다.

행사 하나를 열려면 상권을 만들고, 브랜드를 등록하고, 매장을 붙이고, 계정을 발급한다. 메뉴를 따라가면 네 곳을 오가야 한다. 개시일이 가까울수록 이 왕복이 부담이 된다.

| 기준 | 내용 |
| --- | --- |
| 상권 상세 | 상권 하나를 열면 그 안에서 소속 매장과 등록 상태를 함께 본다. 준비 현황은 대시보드에서 본다 |
| 상위 항목 추가 | 하위를 만들다 상위가 없으면 그 자리에서 만든다. 상권 선택 칸에서 상권을 새로 만들 수 있다 |
| 반복 개설 | 이전 행사의 상권과 매장 구성을 복제한다. 매번 처음부터 만들지 않는다 |
| 대량 등록 | 매장은 파일로 한 번에 올린다. 한 행사에 수십 개가 들어온다 |
| 조회 조건 유지 | 목록에서 상세로 갔다 돌아오면 조건과 페이지와 스크롤 위치를 되살린다 |
| 빈 상태 | 결과가 없을 때 다음에 할 일을 함께 제시한다. 문구만 남기지 않는다 |
| 일괄 처리 | 목록에서 여러 건을 골라 상태를 한 번에 바꾼다. 대상 건수를 확인 팝업에 적는다 |

#### 왜 상권 상세를 두는가

매장은 상권에 속한다. 매장을 따로 관리하면 어느 상권의 매장인지 매번 조건을 걸어 찾아야 한다.

상권 상세는 그 상권에 속한 매장을 한 화면에 모은다. 등록과 상태 전환을 그 자리에서 처리한다. 행사 단위의 개시 준비 현황은 대시보드에서 본다.

#### 조회 조건을 유지하는 이유

매장 38개를 검수하는 작업은 목록과 상세를 서른여덟 번 오간다. 돌아올 때마다 조건이 초기화되면 매번 다시 걸러야 한다.

브라우저 뒤로 가기와 화면 안의 목록 버튼이 같게 동작해야 한다. 둘이 다르면 사용자가 어느 쪽을 눌러야 할지 매번 판단하게 된다.

## 3. 의사결정 사항

### DC-001 결제·정산 계약 구조

* 배경: 본사가 가맹점 대금을 수취해 정산하면 전자지급결제대행업 등록 대상이 될 수 있다. 미등록 시 3년 이하 징역 또는 2천만원 이하 벌금이다.
* 결정: 외부 결제대행사가 정산을 전담한다. 플랫폼은 대금을 수취하지 않고 정산에 필요한 정보만 제공한다. 각 매장을 결제대행사의 하위가맹점으로 등록하고 플랫폼은 대표가맹점이 되지 않는다.
* 근거: 금융위원회가 2024년 6월 보도설명자료에서 등록이 필요 없는 사례로 명시한 구조다. 기준은 2.7에 있다.
* 상태: 확정. 계약 체결 전 법무 검토를 거친다

### DC-002 메뉴 기준의 위치

* 배경: 업계는 POS가 기준이다. 본 서비스는 ERP가 기준이다. 매장이 POS에 직접 등록한 메뉴와 충돌할 수 있다.
* 결정: 매장이 우리 화면에서 등록한 메뉴를 유일한 기준으로 둔다. 외부 POS는 조회만 하고 등록과 수정을 할 수 없다. 양방향 동기화를 두지 않는다.
* 근거: 조사한 제품들이 양방향 동기화를 위험한 작업으로 경고한다. 기준을 하나로 고정하면 충돌 처리 규칙 자체가 필요 없다. 제공 규격은 2.2에 있다.
* 상태: 확정

### DC-003 메뉴 변경의 반영 시점

* 배경: 배포를 없애고 매장이 메뉴 원본을 갖기로 하면서 발행 시점을 고르는 문제가 사라졌다. 남은 것은 각 채널이 언제 새 값을 읽느냐다.
* 결정: 저장과 반영을 분리하지 않는다. 매장이 저장하면 반영된다. 채널별 확인 시점은 웹앱 즉시, 키오스크는 유휴 시점과 결제 완료 시점, 외부 POS는 통지 후 조회로 둔다.
* 근거: 키오스크는 주문 중 화면이 바뀌면 고객이 고른 값과 결제 금액이 달라진다. 진행 중 주문은 기존 가격으로 처리한다. 기준은 2.4에 있다.
* 상태: 확정

### DC-004 주문 접수 화면의 위치

* 배경: POS가 범위 밖이므로 스마트오더 주문을 받을 화면이 필요하다.
* 결정: 가맹 어드민 안에 주문 접수 화면을 둔다. 별도 매장 전용 화면을 만들지 않는다.
* 근거: 매장이 쓰는 화면을 두 개로 나누면 계정과 권한을 이중으로 관리해야 한다. 접수와 메뉴 관리는 같은 담당자가 한다. 주방 확인은 화면이 아니라 주문서 출력으로 처리한다.
* 상태: 확정

### DC-015 이상 알림 발송 범위

* 배경: 대시보드에 이상 감지를 두었으나 화면을 열지 않으면 알 수 없다. 네 가지 이상 유형 중 무엇을 알림으로 보낼지 정해야 한다.
* 결정: 단말 미연결만 보낸다. 30분에 매장, 60분에 본사로 2단계로 나눈다. 나머지 세 유형은 화면에만 둔다.
* 근거: 받는 사람이 취할 구체적 조치가 있는 건만 보낸다. 접수 지연과 품절은 매장의 운영 상황이고 본사가 할 일이 없다. 매출 급락은 장애와 한산함을 구분하지 못한다.
* 상태: 확정

### DC-005 메뉴 등록 주체

* 배경: 조사한 14개 제품 모두 가맹점 승인 절차가 없다. 본사 마스터 모델과 매장 소유 모델 중 하나를 고른다.
* 결정: 매장이 자기 메뉴를 등록하고 관리한다. 본사는 메뉴를 만들지 않는다. 내려보낼 원본이 없으므로 배포 절차와 승인 절차를 두지 않는다. 본사는 표시 정보 검수로만 관여한다.
* 상태: 확정

### DC-006 알레르기 정보의 등록 단위

* 배경: 어느 제품에도 알레르기 필드가 없다. 업계는 옵션별 알레르기를 상품 복제로 처리한다.
* 결정: 메뉴 단위로 등록한다. 옵션이 알레르기 유발물질을 바꾸면 조합별로 상품을 복제해 각각 등록한다. 복제 관계를 기록해 원 메뉴 수정 시 복제본을 확인 대상으로 표시한다.
* 상태: 확정
